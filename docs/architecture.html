01 · ARCHITECTURE

구성 요소와 호출 관계

모든 호스트 연동은 register.ts 한 곳에 모여 있고, 상태 전이는 호스트를 모르는 순수 함수인 hooks/engine이 맡습니다. 메인 모델은 직접 편집하지 않고 dag 도구로 런타임에 실행을 맡기며, 실제 작업은 런타임이 띄운 노드 워커가 합니다.

런타임 register.ts가 하는 일

06 · SEQUENCE

한 번의 실행 시퀀스

start는 실행을 기다리지 않고 바로 스냅샷을 돌려줍니다. 이후 웨이브는 워커의 turn.complete 훅 안에서 이어서 띄웁니다. 타이머 콜백에서 띄운 워커는 플러그인이 이벤트를 받지 못하기 때문에, 후속 웨이브를 훅 프레임 안에서 띄우는 것이 설계상 필수입니다.

tick 루프 register.ts:1175

  1. advance로 대기 노드를 예약하거나 건너뜀
  2. 첫 생성 전에 persist
  3. nextToStart: 승인 대기면 0개, 아니면 최대 동시 8 − 실행 중
  4. 사용량이 usage_hold_percent(90) 이상이면 생성 보류
  5. 노드마다 startNode 후 다시 persist
  6. 판정 FAIL로만 실패해 정착하면 리뷰 수정 라운드 시도 후 반복
  7. 처음 정착하면 trajectory 기록, 알림, announce

08 · COMPLETION

완료 처리와 자동 복구

onAgentDone은 완료를 직렬 큐에서 점유한 뒤, 보고서 쓰기와 검사는 큐 밖에서 하고 다시 큐 안에서 applyCompletion으로 반영합니다. 검사 결과는 통과, 실패, 실행 안 됨(not_run), 판정 불가(unknown)로 나뉘며 모두 통과해야 완료입니다.

자동 복구 register.ts:1928, recovery.ts:37

  • Jev가 실패를 transient·implementation·missing-input·clarification·permanent로 분류
  • jev_recovery_confidence(0.9) 이상인 transient·implementation만 재시도
  • implementation, 이전 시도나 원래 경로가 opus였으면 opus로 올림
  • 재시도 프롬프트에 [Recovery n/2], 검증 증거, 이전 시도의 Next:·Tried and failed: 첨부
  • 노드당 최대 2회 (MAX_AUTO_RECOVERIES)

리뷰 수정 라운드 rework.ts:126

  1. run이 판정 FAIL로만 실패해 정착했고 라운드가 아직 0회
  2. 각 리뷰어에서 위로 올라가 완료된 생산 노드를 찾고, 지적에 나온 경로가 writes에 들어가는 노드를 고름
  3. 외부 부작용 위험(external, 이름에 delete·commit·email 등, writes 없음)이 있으면 건너뜀
  4. 생산 노드는 원래 에이전트에 $.session.send로 지적을 보내 재개, 실패하면 새 에이전트
  5. 다시 실행된 리뷰어는 보낸 지적과 수정 diff(최대 12,000자) 원장을 받음 ledger.ts
09 · STAGES

자동 생성 검토 단계

정의에 review나 commit을 넣으면 expandStages가 사용자 노드 뒤에 검토 노드를 덧붙입니다. 보안 렌즈가 찾은 후보마다 반박 검증 노드는 실행 중에 생기며, 이때 판정 노드가 아직 대기 상태여야 합니다. 그림의 화살표는 결과가 흐르는 방향입니다.

PART III

Claude Code Mod로서의 dag-workflow

Mod는 Claude Code 엔진 안에서 실행되는 훅 모듈을 가진 플러그인입니다. 엔진이 이벤트를 낼 때마다 Mod의 핸들러가 끼어들어 관찰하거나, 값을 바꾸거나, 흐름을 막습니다. dag-workflow의 모든 동작은 이 접점 위에 있습니다.

14 · MOD

Claude Code Mod란

엔진은 hooks.json에 적힌 모듈을 불러와 register(on, options)를 한 번 부릅니다. 모듈은 on(event, filter?, handler)로 핸들러를 등록하고, 핸들러는 ($, e, next)를 받습니다. $는 호스트 API, e는 이벤트 값, next는 아래 훅과 엔진 코어로 넘기는 함수입니다.

매니페스트와 설정

  • .claude-plugin/plugin.json의 userConfig가 설정 화면의 항목이 됨
  • 값은 options로 들어오고 register 첫머리에서 범위를 검사해 읽음 register.ts:3363–3411
  • 예: enforcement(기본 auto), max_concurrent(8), jev_confidence(0.9), trajectory_log(끔)

모듈이 도는 환경

  • DOM도 Node도 없는 별도 환경. ES 모듈만, require와 동적 import() 없음
  • 파일·프로세스·네트워크는 모두 $.fs, $.process, $.http로만
  • 렌더 요소(Box, Text, Button)는 전역이 아니라 $.ui.resolve(e)로 받음

상태와 재로드

  • /reload-plugins는 모듈 변수를 모두 초기화함
  • 그래서 planning 로드 표시는 $.state(PluginState)에 두어 재로드 뒤에도 유지 register.ts:194, 210
  • 패널 선호와 세션 레지스트리는 프로젝트 범위 키로 $.store에, run은 파일로 저장

16 · MIDDLEWARE

훅 미들웨어 체인

훅은 미들웨어처럼 쌓입니다. 핸들러가 next(e)를 부르면 아래 훅과 엔진 코어가 실행되고, 부르지 않고 값을 돌려주면 그 자리에서 흐름이 끝납니다. 메인 루프 게이트는 이 성질로 도구 실행 전에 거부를 돌려줍니다.

이벤트별 응답 형태

  • tool.call: { deny }로 거부, { result }로 대신 답함
  • tool.check: { decision }으로 권한 판정
  • prompt.submit: { drop }으로 프롬프트 차단, 또는 텍스트 수정
  • agent.spawn: { model } 지정 또는 { deny }
  • command.run, skill.prompt: { text }로 출력·본문 교체

필터로 범위 좁히기

  • on('tool.call', { tool: 'Bash' }, …) kill-guard :4178
  • on('tool.call', { tool: /^(?:Edit|Write)$/ }, …) semgrep·anti-slop :4151, :4188
  • on('ui.render', { component: 'Pane' }, …), { component: 'AbovePrompt' } :4112, :4119
  • 워커와 메인은 e.agentId 유무로 구분

실패하면 닫기

  • 엔진은 예외가 난 훅을 건너뛰고 도구를 실행함
  • 그래서 게이트 훅에 .catch를 달아, 실패 시 순수 검사만으로 다시 판정하고 막힘 쪽으로 닫음 :3978–3991
  • 정착 알림처럼 기다리면 안 되는 일은 serialized 큐 밖으로 뺌

Mod 검증과 지켜야 할 규칙

Mod는 세션 안에서 실행되기 전에 정적으로 검사하고, 엔진과 같은 환경에서 테스트합니다. 아래 규칙들은 실제 실행에서 문제가 확인된 뒤 코드와 문서에 고정된 것입니다.

검증 명령

  • claude plugin validate .: 매니페스트와 훅 모듈 소스를 엔진처럼 읽어, 무엇을 훅하고 부르는지와 거부될 항목을 보고
  • claude plugin test: claude-code/testing으로 엔진과 같은 환경(파일·네트워크·프로세스 없음)에서 실행. mock.clock과 clock.settle()로 비동기 진행

  • claude --plugin-dir .: 실제 세션에 불러오기

지켜야 할 규칙

  • 워커 생성을 $.clock.after·every 콜백으로 옮기지 않음. 그렇게 띄운 워커의 이벤트를 이 Mod가 받지 못함
  • wait 도구는 막지 않고 스냅샷을 돌려줌. 정착은 알림으로 전달
  • serialized 안에서 다시 serialized를 부르지 않음. 큐가 교착됨
  • 폭은 대화 폭이 아니라 surface.columns, 길이는 문자 수가 아니라 표시 폭으로 잼
