# 사용법과 설정 레퍼런스

[README로 돌아가기](../README.md)

전체 명령, DAG 정의와 검증 문법, 실행 규칙을 설명합니다. 명령과 코드 경로는 프로젝트 루트 기준입니다.

## 불러오기

```bash
claude --plugin-dir /path/to/this-project
```

플래그 없이 모든 세션에서 항상 불러오려면 `~/.claude/settings.json`의 `env`에 플러그인 경로를 넣습니다. 이렇게 하면 어느 디렉터리에서 시작하든 강제와 계획 스킬이 켜진 상태로 시작합니다. `--plugin-dir`을 함께 줘도 한 번만 불러옵니다.

```json
{
  "env": {
    "CLAUDE_CODE_PLUGIN_DIRS": "/path/to/this-project"
  }
}
```

## 사용법

**평소처럼 요청하기**: 따로 말하지 않아도 노드가 셋 이상 필요한 작업은 Claude가 DAG로 계획해 `mcp__dag-workflow__dag` 도구로 실행합니다(작은 요청은 기본값 `auto`가 직접 실행합니다. [강제](#강제)). `start`는 바로 반환되고, 실행이 끝나면(정착하면) 노드별 결과가 담긴 요약 메시지가 세션에 들어옵니다.

**파일로 실행하기**:

```text
/dag run flows/review.yaml      JSON 또는 YAML 정의 파일 실행
/dag preview <file>             정의 파일을 실행하지 않고 단계·모델·쓰기 충돌·경고 미리보기
/dag                            DAG 패널 열기
/dag list                       이 프로젝트의 실행 목록
/dag status <run_id>            노드별 상태
/dag cancel <run_id>            실행 취소(실행 중인 노드 에이전트 중단)
/dag retry <run_id> [node...]   실패/취소된 노드 다시 실행
/dag enforce [strict|auto|guide|off] 이 세션의 강제 수준 확인·변경(auto일 때는 이번 턴의 방식도 표시)
/dag view [auto|graph|lanes|timeline]  그래프 영역의 보기 확인·변경(이 프로젝트에 저장)
/dag inspect dag|decisions|context|sessions|board  패널을 그 화면으로 열기
/dag context                    이 세션의 복원 컨텍스트(JSON) 보기
/dag note <text>                고정 노트 추가(1-4000자, 최대 50개)
/dag note rm <번호>             고정 노트 삭제(번호는 /dag context에 보이는 1부터 시작하는 순서)
/dag decisions [id]             최근 판단 20개 또는 판단 하나의 전체 기록
/dag sessions                   같은 프로젝트의 세션과 겹치는 쓰기 범위
/dag handoff <run> <session>    실행을 다른 세션에 넘기겠다고 제안
/dag handoff <run> cancel       보낸 제안 취소
/dag accept <run>               나에게 온 제안 수락
/dag approve <run>              승인 대기 중인 실행을 승인하고 시작
/dag reject <run> [reason]      승인 대기 중인 실행을 거부하고 취소(사유는 모델에 전달)
/dag approval [off|always]      모델이 시작한 실행의 승인 설정(start_approval) 확인·다음 `/reload-plugins`까지 변경
/dag learn                     아직 학습하지 않은 세션 경험으로 백그라운드 학습
/dag learning [status|on|off|prune] 학습 상태 확인·현재 세션 켜기/끄기·미사용 스킬 보관
```

`handoff`, `accept`, `note`, `approve`, `reject`는 사용자가 직접 입력하거나 패널 버튼을 눌러야 실행됩니다. `approval`은 읽기와 쓰기가 다릅니다. 인자 없이 `/dag approval`로 지금 값을 읽는 것은 누구에게나 열려 있고, `/dag approval off|always`로 바꾸는 것만 사용자 전용입니다. 사용자 전용 명령은 모델이 대신 실행할 수 없습니다.

`/dag run`과 `/dag retry`를 모델 턴이 진행 중일 때 입력하면 정의를 바로 검증하고 실행을 보류 상태로 저장한 뒤, 그 턴이 끝날 때(중단된 턴 포함) 시작합니다. 모델이 턴 안에서 호출하는 `dag` 도구는 계속 즉시 시작합니다.

## 세션 학습

`session_learning`의 기본값은 `true`입니다. 플러그인을 불러온 세션 전체에서 사용자 프롬프트, 허용된 도구 호출의 입력·결과, 메인 및 일반 서브에이전트의 최종 답변을 수집합니다. DAG 실행 여부나 `enforcement` 설정과 독립적입니다. 플러그인을 불러오지 않은 세션이나 다른 사용자의 기록은 읽지 않습니다.

사용자 요청에 대한 메인 답변이 정상 종료되면 미학습 경험을 Sonnet 에이전트에 전달합니다. 서브에이전트의 턴이 끝났을 때도 `learning_interval`개 이상의 도구 호출이 쌓이면 학습을 시작합니다. 학습은 백그라운드이며, 에이전트는 도구를 실행하지 않고 주어진 근거로 JSON 변경안만 반환합니다. 학습 자체의 호출·답변과 플러그인의 진행 알림은 다시 학습하지 않습니다. 사용량은 사용자의 Claude 요금제에 포함됩니다.

학습 대상은 재사용할 해결 방법, 사용자의 교정과 작업 선호입니다. 단순 작업 요약과 검증되지 않은 실패한 해결책은 제외하도록 지시합니다. 변경안은 스킬 이름·필드·크기·근거 이벤트·적용 범위를 검사한 뒤 저장합니다. 이 검사는 학습 내용의 사실성을 보증하는 것은 아닙니다. 비밀값은 기존 마스킹 규칙으로 가리고, 수집 자료는 세션당 80개 이벤트·60,000자로 제한하되 최신 사용자 요청을 남깁니다. 긴 작업에서도 요청이 밀려나 학습이 중단되지 않습니다.

전체 학습 프롬프트는 지침·근거·기존 스킬 원문을 합쳐 `learning_max_input_chars`(기본 60,000자) 이내입니다. 한 번에 들어가지 않는 미학습 자료는 순서대로 나누고, 에이전트 시작 전에 자료와 완료 위치를 함께 고정합니다. 시작 중 새로 들어온 교정은 다음 배치에 남습니다. 기존 스킬은 원문 전체가 전달된 경우에만 수정·통합할 수 있습니다.

자동 학습 시도는 모든 사용자 세션을 합쳐 UTC 하루 `learning_max_daily_runs`번(기본 20회)으로 제한합니다. 시작 전에 횟수를 예약하므로 시작·응답이 실패한 시도도 포함됩니다. 한도에 도달해도 미학습 자료는 수집 한도 내에서 남기며, 사용자가 직접 입력한 `/dag learn`은 일일 자동 실행 제한만 우회합니다. 모델이나 다른 플러그인의 명령 호출은 우회하지 않습니다. 이 설정은 실행 횟수 제한이지 정확한 금액 상한은 아닙니다.

저장 위치는 `HOME` 기준입니다.

- `~/.claude/skills/dag-learned-<이름>/SKILL.md`: 생성한 스킬.
- `~/.claude/dag-workflow/learning/library.json`: 적용 범위, 사용량, 변경 이유와 원본 세션·이벤트 식별자. 스킬별 변경 이력은 최근 20개.
- `~/.claude/dag-workflow/learning/sessions/`: 세션별 수집 자료와 실행 중인 학습 배치. 같은 세션을 재개하면 이어서 사용.
- `~/.claude/dag-workflow/learning/archive/`: 통합되거나 미사용으로 보관 처리된 스킬. 보관하거나 기간이 지나 정리한 뒤 빈 스킬 폴더는 지우고, 사용자가 넣은 다른 파일이 있는 폴더는 남깁니다.
- `~/.claude/dag-workflow/learning/pending.json`: 스킬 파일과 인덱스 갱신을 끝내기 위한 복구 기록. 정상 저장 후 제거합니다.

다음 사용자 프롬프트와 서브에이전트의 시작 프롬프트에는 적용 가능한 스킬의 설명과 파일 경로를 제공합니다. 모델은 관련 스킬만 `Read`로 읽습니다. 실행 중 새로 만든 스킬도 이 경로로 사용할 수 있으며, `Skill` 목록에서 인식하는 시점은 호스트의 스킬 검색에 따릅니다. 프로젝트 전용 스킬은 같은 프로젝트에서만 안내하고, 일반 기법은 `global` 범위로 여러 프로젝트에서 재사용할 수 있습니다.

성공한 `Read` 또는 `Skill` 호출을 사용으로 기록합니다. 사용 기회는 적용 가능한 사용자 프롬프트마다 증가하고, 스킬을 사용하면 미사용 기회 수를 초기화합니다. `learning_min_opportunities`번의 기회 동안 사용하지 않은 스킬은 보관합니다. `learning_max_skills`를 넘으면 한 번 이상 노출된 스킬 중 사용량이 적고 오래된 것부터 보관하며, 아직 노출되지 않은 새 스킬은 보호합니다.

수정·통합·보관 대상은 학습 기능이 만든 스킬뿐입니다. 기존 사용자 스킬과 플러그인의 기본 스킬은 관리하지 않습니다. 사용자가 직접 수정한 학습 스킬도 덮어쓰지 않고 로그에 남깁니다. 한 세션 안의 저장은 전용 대기열로 차례로 처리하고, 여러 세션의 저장은 디렉터리 잠금으로 직렬화하며, 같은 스킬을 동시에 갱신했거나 잠금이 사용 중이면 미학습 근거를 남겨 다음 턴에서 다시 학습합니다. 이렇게 실패한 배치는 다음 사용자 턴이 끝나거나, 그 뒤 새 도구 호출이 `learning_interval`개 쌓였을 때 다시 학습합니다. 실패 원인이 계속 남아도 턴이 끝날 때마다 학습 에이전트를 띄우지 않습니다. 저장 직전 검사가 실패하면 근거를 남기고 저장했다는 로그를 쓰지 않습니다.

모든 변경 대상 파일을 확인한 뒤 복구 기록을 먼저 저장하고 스킬 파일·인덱스를 갱신합니다. 도중에 중단되면 다음 저장이나 세션 시작 때 갱신 전·후의 내용과 일치하는 파일만 이어서 처리합니다. 중간에 사용자가 직접 고친 파일은 보존하고 그 스킬만 건너뛴 채 나머지 갱신과 복구 기록 정리를 마칩니다. 복구 기록이 남아 이후 모든 세션의 학습 저장을 막지 않게 하기 위해서입니다. 학습 자료 저장 실패는 로그에 남기고 메인 턴과 DAG 노드의 완료 처리는 계속합니다.

시작할 때와 `/dag learning prune` 실행 때 `learning_retention_days`(기본 30일)보다 오래된 다른 세션 자료와 보관된 스킬·이력을 정리합니다. 현재 세션, 실행 중인 학습 배치가 남은 세션, 활성 스킬, 사용자가 직접 고친 보관 파일은 보호합니다. `0`이면 기간에 따른 삭제를 하지 않습니다.

`/dag learn`은 미학습 자료로 지금 학습을 시작합니다. `/dag learning`은 상태와, 이 프로젝트에서 쓸 수 있는 스킬(`global`과 이 프로젝트 전용)의 변경 근거를 보여 줍니다. 모델도 실행할 수 있으므로 스킬 본문은 넣지 않으며 본문은 각 `SKILL.md`에서 봅니다. `on|off`는 현재 세션의 학습·재사용 안내를 켜거나 끕니다. `prune`은 같은 보관 정책을 바로 적용합니다. `on|off|prune`은 사용자가 직접 입력해야 합니다. 세션 종료 시 긴 학습을 새로 시작하지 않고 자료를 저장합니다. 미학습 자료는 같은 세션 재개 후 다음 학습에 포함됩니다.

## 강제

기본값인 `auto`에서는 사용자 프롬프트마다 Jev가 요청을 DAG로 돌릴지 바로 실행할지 판단합니다. 노드가 셋 이상 필요하고 병렬 또는 격리 실행으로 이득을 보는 요청이면 DAG로, 그렇지 않은 작은 요청이면 메인 대화에서 직접 실행합니다. 이 판단은 판단 종류 `mode`(패널과 `/dag decisions`에는 **실행 방식**)로 [기록](#판단-기록)됩니다. 같은 호출이 답을 채팅과 보드 중 어디에 보여 줄지도 판단합니다([표시 방식 판단](#표시-방식-판단)).

- **직접 실행 턴**: 아래 1번 도구 게이트가 풀려 메인 대화가 Edit, Write, 쓰기 Bash 같은 도구를 직접 호출합니다. 호출은 사용자의 평소 권한 규칙을 그대로 따릅니다. 프로토콜은 "이 요청은 작으니 DAG 없이 직접 하라"는 한 줄로 바뀌고, 독립된 작업이 셋 이상으로 커지면 계획 스킬을 불러 DAG로 돌리라고 알립니다.
- **DAG 턴**: 아래 네 가지가 `strict`와 똑같이 동작합니다. 프로토콜에는 Jev가 DAG로 판단했거나 이 세션에 정착하지 않은 실행이 있다는 한 줄이 더 붙습니다.
- **DAG 턴이 되는 경우**: Jev가 확신도 0.8 이상으로 DAG라고 판단했을 때와, 이 세션에 아직 정착하지 않은 실행이 있을 때 두 가지뿐입니다. 뒤의 경우에는 Jev를 부르지도 않습니다. 직접 실행 턴이 그 실행의 노드가 쓰는 파일을 건드릴 수 있기 때문입니다. 그 밖에는 모두 직접 실행 턴입니다: Jev가 직접 실행으로 판단했을 때, 확신도가 0.8 미만일 때(어느 쪽으로 기울었든), Jev를 쓸 수 없을 때(`jev_enabled`가 꺼졌거나 키도 세션 모델 대체도 없음), 답이 제한 시간 안에 오지 않았거나 잘못됐을 때. 그래서 Jev를 쓸 수 없는 환경의 `auto`는 정착하지 않은 실행이 없는 한 모든 턴을 직접 실행합니다. 예전에는 판단하지 못한 턴을 모두 DAG로 돌렸는데, 기록된 실행 방식 판단 10건 중 DAG 턴 5건의 4건이 확신 있는 DAG 판단이 아닌 이런 대체였고 작은 요청까지 막았기 때문에 바꿨습니다.
- **판단 시점**: 사용자 프롬프트마다 새로 판단하고, 직접 실행 턴에서 선택 창에 답했을 때도 한 번 더 판단합니다(아래 **선택 창 답**). 플러그인이 보내는 프롬프트(정착 요약, 진행 알림, keep-alive)는 판단하지 않고 현재 턴의 방식을 그대로 씁니다. 사용자 프롬프트는 답이 올 때까지 기다리며 기다림은 최대 8초입니다(TypeSafe와 세션 모델 대체를 합친 한도로, [Jev 섹션](#jev-를-활용한-자동-판단)의 5초·10초 제한과 별개). 판단하는 동안에는 게이트가 닫혀 있고, 답이 없거나 실패하면 직접 실행 턴이 됩니다. 판단 코드 자체가 예외로 끊긴 경우만 게이트가 닫힌 채로 남습니다.
- **선택 창 답**: 직접 실행 턴에서 사용자가 AskUserQuestion 선택 창에 답하면 Jev가 질문과 선택지, 고른 답을 사용자의 직전 요청 최대 3개와 함께 다시 판단합니다. 고른 작업이 DAG를 필요로 하면 그 턴은 그 자리에서 DAG 턴이 되어 도구 게이트가 닫히고, 모델은 도구 결과 뒤에 계획을 짜서 실행을 시작하라는 안내를 받습니다. 한쪽으로만 바뀝니다. 선택 창 답이 DAG 턴을 직접 실행 턴으로 풀지는 않는데, 범위 A·B를 고르는 좁은 계획 질문은 작게 판단되어도 실제 작업은 클 수 있기 때문입니다. 프롬프트와 같은 규칙으로, 확신도 0.8 이상의 DAG 판단이나 이 세션의 정착하지 않은 실행만 DAG 턴을 만들고, 확신도 0.8 미만, 제한 시간(8초) 초과, Jev를 쓸 수 없는 경우는 직접 실행 턴을 그대로 둡니다. 사용자는 답한 뒤 판단이 끝날 때까지 최대 8초를 기다립니다. 이 판단은 종류 `mode`, 대상 `answer`로 [기록](#판단-기록)됩니다(프롬프트는 대상 `request`).
- **직접 실행 턴에서 실행 시작**: 직접 실행 턴에서 모델이 `start`하거나 사용자가 `/dag run`을 입력해 실행이 만들어지면 그 턴은 DAG 턴이 되어 게이트가 다시 닫힙니다. `amend`와 `retry`는 턴을 바꾸지 않습니다. 계획 스킬 게이트(아래 4번)는 `auto`에서도 `strict`처럼 적용됩니다.
- **알려진 한계**: 모델이 일하는 도중에 입력한 프롬프트도 Enter를 누른 때 판단하므로 아직 진행 중인 턴의 게이트가 바뀔 수 있습니다. 예를 들어 직접 편집하던 턴에 DAG로 판단되는 요청을 이어 입력하면 진행 중이던 편집이 거부될 수 있습니다.

`strict`는 모든 턴에 DAG 턴 규칙을 적용합니다. 네 가지는 다음과 같습니다.

1. **도구 게이트**: 메인 대화에서 모델이 호출하는 도구 중 다음을 제외한 모든 도구를 거부합니다. 거부할 때는 "이 작업을 DAG 노드로 옮겨 `start`나 `amend`하라"는 안내를 돌려줍니다.
   - 허용: dag 도구, [board 도구](#보드)(`mcp__dag-workflow__board`. 패널에 그리고 프로젝트 파일을 읽기만 합니다), Read, LSP, WebFetch/WebSearch, AskUserQuestion, 계획 모드, 작업 조회·중단(TaskList/TaskGet/TaskStop), 읽기 전용 Bash, 호스트가 막는 보고서 이름에 한정한 Write 예외(아래)
   - 읽기 전용 Bash: `ls`, `cat`, `rg`, `find`(‐exec/‐delete 제외), `git status/log/diff/show/...`, 인자가 `--version`/`--help` 하나뿐인 명령, 맨 앞의 `command` 내장 명령(`command claude --version`, `command git status`처럼 뒤따르는 명령은 그대로 검사하며 `command -v`·`command -p`는 거부), `uv pip list/freeze/show/check`, 출력만 하는 `sed`(`-i`·`-f`·`w`·`e` 제외) 등. 목록에 있는 명령도 파일을 쓰거나 프로그램을 실행하는 형태는 거부합니다: `fd`의 `-x`/`-X`/`--exec`/`--exec-batch`, `rg`의 `--pre`·`--hostname-bin`, `tree`의 `-o`·`-R`, `sort`의 `-o`/`--output`·`--compress-program`, 피연산자를 둘 이상 받아 두 번째 파일에 쓰는 `uniq`, `file`의 `-C`/`--compile`, 모든 읽기 전용 `git` 하위 명령의 `--output`·`--ext-diff`와 `git grep`의 `-O`/`--open-files-in-pager`. `git`은 하위 명령 앞에 `-C`, `--git-dir`, `--work-tree`, `--no-pager`/`-P`, `--no-optional-locks`, `--literal-pathspecs`, `--glob-pathspecs`, `--noglob-pathspecs`, `--icase-pathspecs`만 받고 그 밖의 전역 옵션(`-c`, `--config-env`, `--exec-path` 등)은 거부합니다. 한 글자 플래그를 묶어 쓴 형태(`sort -uo`)와 긴 옵션의 약어(`sort --out=`)도 같게 거부합니다. 명령 앞의 `변수=값`은 `LC_*`, `LANG`, `LANGUAGE`, `TZ`, `NO_COLOR`, `FORCE_COLOR`, `CLICOLOR`, `COLUMNS`, `TERM`일 때만 건너뛰고, 그 밖의 변수(`PATH`, `LD_PRELOAD`, `GIT_*` 등)는 실행할 프로그램을 바꿀 수 있어 거부합니다(`M=경로; ls $M`처럼 명령 없이 따로 대입하는 줄도 마찬가지입니다). 명령이 모두 읽기 전용이면 `for`/`if`/`while` 구조와 입력 리다이렉트(`< 파일`)도 허용합니다. 출력 리다이렉트(`>`), 명령 치환(`$(...)`), 프로세스 치환(`<(...)`), 목록에 없는 명령이 하나라도 있으면 거부합니다.
   - Write 예외: 파일 이름(basename)이 `REPORT*`, `SUMMARY*`, `FINDINGS*`, `ANALYSIS*`로 시작하는 Markdown(`^(REPORT|SUMMARY|FINDINGS|ANALYSIS).*\.md$`, 대소문자 무시)은 메인 대화의 Write를 허용합니다. Claude Code가 서브에이전트의 이 이름 쓰기를 `Subagents should return findings as text, not write report files`로 직접 거부하므로 노드로는 `report.md` 같은 파일을 만들 수 없기 때문입니다. 정착한 노드의 `## Output`이나 노트를 그대로 옮겨 쓰는 용도로만 허용하며, Edit과 쓰기 Bash, 다른 이름의 Write는 계속 거부합니다.
   - 거부: Edit, Write(위 예외 제외), NotebookEdit, Agent, Workflow, TodoWrite/TaskCreate(계획은 DAG로만), 쓰기 Bash, 그 밖의 MCP 도구
   - DAG 노드 에이전트와 플러그인 자신의 호출(노드 spawn, TaskStop)은 제한하지 않습니다.
2. **프로토콜 주입**: 사용자 프롬프트마다 "계획을 DAG로 짜서 실행하고, 의존 관계를 정확히 적고, 정착 요약을 확인하라"는 짧은 지침을 붙입니다. 비대화형 세션(`session.start`의 `isInteractive`가 false인 경우, 예: `claude -p`)에서는 지침이 한 줄 더 붙어, 사용자에게 묻지 말고(AskUserQuestion도, 확인 질문도 안 됨) 스스로 결정하되 가정을 정의의 `goal`과 노드 프롬프트에 적으라고 알립니다.
3. **도구 설명**: dag 도구 설명에 같은 원칙을 넣습니다.
4. **계획 스킬 게이트**: 세션의 첫 `start`/`amend`는 `dag-workflow:planning` 스킬을 불러오기 전까지 `planning_skill_required`로 거부됩니다([계획 스킬](#계획-스킬)). 게이트가 인정하는 스킬 이름은 `dag-workflow:planning`과 접두사 없는 `planning`뿐이며, 다른 플러그인의 같은 이름 스킬은 인정하지 않습니다. `/clear`하면 다시 불러와야 합니다. `/reload-plugins`는 게이트를 다시 닫지 않습니다(불러옴 여부를 호스트 세션 상태 `$.state`에 보관하므로 핫 리로드를 지나도 남고, 대화를 비우는 `/clear`만 게이트를 닫습니다). `claude --resume`으로 같은 세션을 새 프로세스에서 이어 가도 게이트는 열린 채로 남는데, 플러그인이 불러옴 표시를 세션 컨텍스트 파일 `.claude/dag/context/<세션 id>.json`에도 함께 기록하기 때문입니다. 이 파일은 세션이 DAG를 쓴 뒤(실행을 소유했거나 메모를 고정한 뒤)에야 생기므로, 스킬만 불러온 세션, 새 세션 id를 받는 포크(`--fork-session`), `retention_days`가 지나 컨텍스트 파일이 지워진 세션은 스킬을 다시 불러와야 합니다. 사용자가 직접 실행하는 `/dag run`은 게이트하지 않습니다.

`auto`의 직접 실행 턴은 1을 풀고 2를 위의 한 줄로 바꾸며 3·4는 그대로 둡니다. `guide`는 2·3만 적용하고 스킬을 안 불렀으면 경고만 남기며, `off`는 아무것도 하지 않습니다. 다른 도구를 메인에서 계속 쓰려면 `main_allowed_tools` 설정에 이름을 추가합니다.

### 표시 방식 판단

`auto`에서는 실행 방식을 고르는 바로 그 Jev 호출이 답을 어디에 보여 줄지도 판단합니다. 사용자 프롬프트마다 같은 요청에 질문 하나가 더 실릴 뿐 호출이 늘지는 않으며, 판단 입력도 실행 방식과 같은 요청·직전 요청·직전 답변입니다. 선택지는 채팅(`chat`)과 보드(`board`)입니다.

두 도구의 역할이 다릅니다. DAG는 변경을 만듭니다(병렬 서브에이전트 노드, 격리된 컨텍스트, 검증, 복구). 보드는 사용자가 이해하려는 답(다이어그램, 표, 인용한 코드)을 `/dag` 패널에 남기고 [블록 칩](#블록-칩)으로 프롬프트에 다시 인용하게 합니다. DAG의 수명 주기(시작과 정산)는 보드 도구를 스스로 부르지 않습니다.

- **묻는 조건**: 실행 방식을 Jev에 물을 때만 같이 묻습니다. 이 세션에 정착하지 않은 실행이 있거나 Jev를 쓸 수 없으면(`jev_enabled`가 꺼졌거나 키도 세션 모델 대체도 없음) 실행 방식도 묻지 않으므로 표시 방식도 묻지 않습니다. 그리고 대화형 세션이고 `/dag` 패널이 있는 화면일 때만 묻습니다. 직접 실행 턴에서 선택 창 답을 판단할 때(대상 `answer`)는 묻지 않으며, 그 답이 표시 방식을 바꾸지는 않습니다.
- **확신도 기준**: 확신도 `0.8` 이상의 `board`만 적용합니다.
- **보드가 되는 요청**: 여러 부분으로 이뤄진 무언가를 이해하려는 요청이면서 파일 변경을 요구하지 않는 경우입니다. 시스템이나 흐름이 여러 구성요소에 걸쳐 어떻게 동작하는지, 선택지 비교, 변경이 여러 파일에서 한 일, 트레이드오프가 있는 결정, 발견 자체가 산출물인 조사가 해당합니다.
- **채팅인 경우**: `strict`, `guide`, `off`와 그 밖의 모든 경로(`chat` 판단, 확신도 `0.8` 미만, 제한 시간 초과, 잘못된 응답, 위 조건을 채우지 못한 경우)에서 표시 방식은 채팅이고, 프로토콜도 표시 방식을 알지 못하던 때와 같습니다.
- **직접 실행 + 보드**: 프로토콜이 메인 대화에서 보드로 답하라고 알립니다. 도구가 지연 로드 상태면 ToolSearch로 불러오고, 섹션 하나와 다이어그램 하나, 인용한 줄을 그린 뒤 `open`하고, 채팅 답은 보드를 가리키는 몇 줄로 줄입니다. 이 안내는 게이트가 아닌 권장이라 도구를 쓸 수 없거나 `edit`가 두 번 거부되거나 `open`이 `shown: false`를 돌려주면 채팅으로 답합니다.
- **DAG + 보드**: 실행은 평소대로 돕니다. DAG 턴의 프로토콜에 "정착한 실행을 검증한 뒤 발견을 보드에 그리라"는 줄이 더해지고, 정산 메시지도 모델에게 검증한 발견을 보드에 그리고 `open`하라고 알립니다. 정산 때 플러그인이 보드를 그리지는 않습니다. `open`은 [보드 섹션](#보드-섹션)의 규칙을 따라, 그 뒤에도 이 세션에 끝나지 않은 다른 실행이 있으면 패널이 DAG에 머물고 토스트만 띄웁니다.
- **메모리에만 있는 연결**: 어느 실행이 보드로 보여 줄 실행인지는 메모리에만 두고 체크포인트에 저장하지 않습니다. 세션을 재개하거나 플러그인을 다시 로드하면 사라지므로, 그 뒤 정산하는 실행은 보드 안내 없이 채팅으로 보고합니다.
- **기록**: 판단은 종류 `surface`(패널과 `/dag decisions`에는 **표시 방식**)로 [기록](#판단-기록)됩니다. 선택값은 `chat` 또는 `board`이고, 확신도가 `0.8` 미만이어서 채팅으로 남은 판단도 기록됩니다.

`skills/planning/`이 플러그인에 들어 있습니다(`/dag-workflow:planning`).

- `SKILL.md`: 언제 쓰나, 정의 형태(노드 필드, dependsOn으로 결과가 흐르는 방식), 목표 우선, 실행·복구(retry/amend/send/cancel)·감독 방법, 메인 대화가 할 수 있는 일
- `SKILL.md`의 `## Alignment` 단계: 계획 읽기 뒤, 실행 계획을 쓰기 전에 질문 라운드를 최대 한 번 가집니다. 산출물 종류(예: CLI인지 문서인지), 범위(들어가고 빠지는 파일·구성요소), 완료 기준 중 하나가 정말 모호하고 Read나 `rg`로도 풀리지 않을 때만 묻습니다. 사실은 찾아보고 묻지 않으며, 모호한 것이 없으면 조용히 건너뜁니다. 라운드는 AskUserQuestion 한 번에 번호 붙인 질문 4개까지이고, 질문마다 추천 답을 첫 옵션으로 두어 "예"만 해도 받아들여집니다. 주입된 프로토콜이 비대화형 세션이라고 알리면 라운드를 건너뛰고 스스로 결정하며 가정은 `definition.goal`과 노드 프롬프트에 적습니다. 요청이 크고 모호하면 `/dag-workflow:interview`나 `/dag-workflow:pm`을 제안할 뿐 모델이 직접 부르지는 않습니다. 답을 받은 뒤 확정한 목표는 `definition.goal`에, 완료 기준은 `verify`에 넣습니다.
- `references/planning.md`: 분해 원칙(TOPOLOGY LOCK, split first, 팬아웃·팬인), 카테고리 사다리, 엣지가 나르는 데이터와 쓰기 범위, 실행 합성, 노드 프롬프트 계약(TASK / DELIVERABLE / SCOPE / VERIFY / STOP WHEN), 검증 웨이브, 실패 대응, 디버그 체인(진단 run 다음 수정 run), 수직 슬라이스와 넓은 리팩터(expand → migrate → contract), 코드 변경 실행의 두 축 리뷰(`review-spec`, `review-standards`)와 선택형 보안 축(`review-security`), 안전하지만 틀린 산출물 점검표
- 노드용 스킬 `skills/anti-slop/`, `skills/debugging/`, `skills/review-standards/`, `skills/secure-coding/`, `skills/testing/`: 노드 정의의 `load_skills`(예: `["dag-workflow:debugging"]`)로 불러오는 작업 규율(의미 없는 코드 차단, 디버깅, 표준 리뷰, 시큐어코딩 관점·검증·집계, 테스트)입니다.

계획 스킬은 검증도 묶어서 하게 합니다. 관련 변경은 한 단계 실행으로 묶고 끝에 검증 단계 하나(코드는 검토 한 쌍, 곧 `review-spec`과 `review-standards`)만 둡니다. 작은 변경마다 검토 한 쌍을 붙이지 않고, 단계 전체는 종단 시나리오 테스트로 증명합니다. 검토 한 쌍과 커밋은 정의의 `review`와 `commit` 필드로 선언하면 플러그인이 노드로 만들어 주므로 손으로 쓰지 않습니다([검토와 커밋 단계](#검토와-커밋-단계)).

mod는 이 스킬을 강제로 연결합니다.  
프로토콜과 거부 메시지가 스킬을 안내하고, strict와 auto에서는 스킬을 불러오기 전까지 첫 계획을 거부하며, `start`와 `amend` 결과의 `warnings`가 계약을 점검합니다. 정의에 `goal`이 없거나 공백뿐이거나(goal 누락, 정의당 경고 하나이며 다른 경고 뒤에 붙고 `goal`은 모든 노드가 봅니다), 노드 프롬프트에 `TASK:`나 `STOP WHEN`이 없거나, 노드가 둘 이상인데 검증 노드(id·label·요약에 verify/validate/check/test/review/audit로 시작하는 단어가 있고 다른 노드에 의존. `preview`는 해당하지 않습니다)가 없거나, 한 노드가 파일 셋 이상을 혼자 만들거나(`writes`와 파일 검사 `verify`의 경로를 세며 테스트 경로는 제외하고, 선언한 폴더와 그 안의 파일은 한 번만 세어 `writes: ['skills/x/']`에 그 안의 파일 둘을 검사하면 둘로 셉니다), 결과 전체를 판정하는 최종 감사(아무 노드도 의존하지 않고 입력이 둘 이상인 검증 노드)가 `trivial`이면 경고합니다. 경고는 실행을 막지 않지만, `trivial`인 최종 감사는 실행할 때 `standard`로 올립니다.

### 정렬 스킬: 인터뷰와 PM

요청이 크고 모호하면 DAG를 짜기 전에 사용자와 먼저 맞추는 스킬 두 개가 있습니다. 둘 다 `disable-model-invocation`이라 사용자가 `/dag-workflow:interview [주제]`나 `/dag-workflow:pm [아이디어]`로 직접 실행할 때만 동작하고, 모델은 스스로 부르지 못합니다(계획 스킬도 제안만 합니다). 메인 대화에서 strict 강제를 받는 것을 전제로 실행하므로 AskUserQuestion, Read, LSP, 읽기 전용 Bash, dag 도구, [board 도구](#보드)만 쓰고 Agent·Write·Edit·쓰기 Bash는 쓰지 못합니다(`auto`에서 직접 실행 턴이면 도구 게이트는 풀리지만 스킬 지침이 같은 도구만 쓰게 합니다). 파일은 스킬이 직접 쓰지 않습니다. 대신 둘 다 질문하는 동안 진행 상황을 보드에 그립니다. 보드는 세션에 남아, 이어지는 실행의 승인 블록이 [계획 보드](#승인-블록의-계획-보드-줄) 줄로 가리킵니다.

- `/dag-workflow:interview`: 요청을 설계 트리로 보고 라운드로 묻습니다.
  - 질문에는 Q1, Q2 번호와 짧은 제목을 붙이고 추천 답을 밝힙니다. AskUserQuestion에서는 추천 옵션을 맨 앞에 "(Recommended)"로 두어 "예"만 해도 받아들여지게 합니다. 앞선 결정이 풀려 지금 물을 수 있는 질문은 한 라운드에 묻되, AskUserQuestion 한 번에 4개까지입니다. 넘치면 하위 가지가 많은 4개를 먼저 묻습니다.
  - 모호함 트랙은 범위, 제약, 산출물, 검증 네 가지입니다. 트랙별 해결됨/미해결 표는 라운드마다 보드에서 갱신하고(아래 **보드에 그리기**), 직전 두 라운드가 한 트랙에만 몰렸으면 가장 덜 다룬 트랙에서 고릅니다.
  - 사실과 결정을 나눕니다. "프로젝트가 X를 쓴다"는 사실이라 Read, LSP, `rg` 같은 읽기 전용 명령으로 직접 찾고, "새 기능이 X를 써야 한다"는 결정이라 사용자에게 묻습니다. 사실이 너무 커서 직접 읽기 어려우면 읽기만 하는 한 노드짜리 DAG로 조사시키고, 기다리거나 폴링하지 않습니다.
  - Refine: 자유 답변에 범위·제약·결정이 담기면 `Decision (user-stated)`, `Constraints (user-stated)`, `My reading`으로 나눠 다시 말하고 AskUserQuestion으로 확인받습니다. 확인 전에는 확정으로 보지 않고, 모델의 추론을 사용자가 말한 것으로 적지 않습니다.
  - Restate gate: 더 물을 질문이 없고 암묵적 가정이 없으면 목표를 한 문장으로, 완료 기준을 관찰 가능한 번호 목록으로 다시 말해 확인받습니다. 보드를 쓰는 중이면 둘을 `Goal and acceptance criteria` 제목의 `section`으로 보드에 넣고(표·트리의 마지막 상태로 바꾸는 `replace`와 같은 `edit` 한 번), `get`으로 읽어 대화와 맞는지 확인한 뒤 AskUserQuestion으로 묻되 질문에 목표 문장을 인용합니다. 고칠 말이 나오면 다시 묻기 전에 그 `section`을 id로 `replace`해 보드가 고친 글을 보여 주게 합니다. 보드를 쓰지 않으면 대화에서 다시 말합니다. "Yes, plan it"을 고른 뒤에만 `dag-workflow:planning`을 불러 넘기며, 목표는 `definition.goal`에, 완료 기준은 `verify` 후보에, 사용자가 말한 제약은 노드 SCOPE 줄에 들어갑니다. 그 전에는 계획할 작업의 `start`를 하지 않습니다.
  - 보드에 그리기: 첫 라운드 전에 도구가 지연 로드 상태면 ToolSearch로 불러오고, `Interview: <주제>` 제목(사용자의 언어, 80자까지)으로 보드를 `create`합니다. `edit` 한 번으로 `Ambiguity tracks` `table`과 `Design tree` `flow`를 넣고 `open`을 한 번 부릅니다. 표는 열이 Track·Settled·Still open이고 행이 Scope·Constraints·Deliverables·Verification입니다. 트리는 결정마다 노드 하나(짧은 id `d1` 등, `label`은 결정 요약, `note`는 `settled: <답>`·`frontier`·`later`, 해결되면 `kind`가 `terminal`이고 아니면 `decision`)이고 한 결정에서 그 아래 걸린 결정으로 간선을 하나씩 긋습니다. 라운드가 시작될 때마다 `edit` 한 번으로 표와 트리를 id로 `replace`하고, 대화에는 표를 다시 찍지 않고 `Board b1, b2 updated: Scope settled, Verification has 2 open items`처럼 한 줄만 남깁니다. 셀과 `note`는 80자, `label`은 40자, 노드는 24개까지이며([블록 종류](#블록-종류)), 넘치면 줄이고 긴 글은 `section`에 두며 노드가 24개를 넘길 듯하면 해결된 말단을 부모의 `note`에 접습니다. 사용자가 블록 id(`b2`)나 트리 노드의 라벨로 짚으면 자유 답변으로 보고 Refine으로 확인합니다.
  - 보드 대신 대화로 돌아가는 경우: 도구를 쓸 수 없거나, `edit`가 두 번 거부되거나, `open`이 `shown: false`를 돌려주면 예전처럼 라운드마다 표를 대화에 출력하고, 그 인터뷰가 끝날 때까지 보드를 다시 쓰지 않습니다.
  - 요청이 이미 명확하면 한 문장으로 알리고 바로 계획 스킬로 갑니다. 비대화형 세션에서는 적용하지 않습니다.
- `/dag-workflow:pm`: 사용자를 제품 책임자로 보고 무엇을, 왜만 묻습니다. 라운드는 `interview`와 같게(번호, 첫 옵션이 추천 답, 한 번에 4개까지) 진행합니다.
  - 질문은 하기 전에 세 분류 중 하나로 가릅니다. 제품 결정(사용자, 문제, 범위, 우선순위, 성공 척도, 사용자에게 보이는 동작)은 사용자에게 묻고, 기술 결정(스택, 구조, 라이브러리, 데이터 모델)은 묻지 않고 "Deferred to development"로 개발 단계에 넘기며, 모름(사용자가 모르거나 다른 사람에게 달렸거나 지금 정할 수 없는 것)은 미해결 항목으로 기록합니다.
  - 제품 질문마다 "Decide later" 선택지를 두고, 고르면 모름으로 취급해 미해결 항목에 넣습니다. 모름을 확정 요구사항으로 내놓지 않습니다.
  - 보드에 그리기: 첫 라운드 전에 도구가 지연 로드 상태면 ToolSearch로 불러오고, `PRD: <아이디어>` 제목(사용자의 언어, 80자까지)으로 보드를 `create`한 뒤 세 목록을 `Product decisions`, `Deferred to development`, `Open items` 제목의 `table` 셋으로 넣고 `open`을 한 번 부릅니다. 표마다 열은 `Item`과 `Source`이고 `Source`는 `user` 또는 `Q3` 같은 질문 번호입니다. 라운드가 끝날 때마다 바뀐 표만 새 행 전체로 `edit` 한 번에 `replace`하고, 대화에는 목록을 다시 찍지 않고 `Updated b2 and b3 (Q1-Q4)`처럼 바뀐 블록을 한 줄로 알립니다. 셀은 80자, 표는 30행까지이며([블록 종류](#블록-종류)), 더 긴 목록은 같은 열의 표를 하나 더 둡니다.
  - 보드 대신 대화로 돌아가는 경우: 도구를 쓸 수 없거나, `edit`가 두 번 거부되거나, `open`이 `shown: false`를 돌려주면 보드를 쓰지 않고 세 목록을 예전처럼 대화에 두며, 확인 단계에서 다시 보여 줍니다.
  - 질문이 끝나면 확정한 제품 결정, 미룬 기술 결정, 미해결 항목과 제품 목표 한 문장을 보여 주고 확인받은 뒤에야 씁니다. 보드를 쓰는 중이면 목표를 `Product goal` 제목의 `section`으로 보드에 넣고 `get`으로 읽어 항목·출처·목표가 대화와 맞는지 확인한 뒤, 보드를 가리키며 AskUserQuestion 한 번으로 목록과 목표를 확인받습니다. 사용자가 항목을 고치면 보드를 `edit` 한 번으로 고치고 다시 확인받습니다.
  - PRD 파일은 메인 대화가 쓸 수 없으므로 노드가 하나인 DAG `write-prd`(category `writing`, `writes`는 `docs/prd/<slug>.md`)가 씁니다. 계획 스킬을 먼저 불러 시작합니다. 노드는 Problem, Users, Goals, Scope, Requirements, Success criteria, Deferred to development, Open items 순서의 섹션을 쓰고, 미해결 항목은 `## Open items`에만 적으며 비어 있어도 "None"으로 이 섹션을 씁니다. 검증은 그 파일에 `## Open items`와 `## Goals`가 들어 있는지 확인합니다. 정착하면 PRD를 읽어 경로와 미해결 항목을 보여 주고, 다음 단계로 `/dag-workflow:interview`나 일반 계획을 제안합니다.

## 결과 전달

- 노드는 최종 보고서를 `## Output` 섹션(만든 파일, 핵심 사실·값·결정)과 `DAG_NODE_STATUS` 줄로 끝내도록 지시받습니다.
- 노드가 끝나면 전체 보고서는 `.claude/dag/runs/<run_id>/<node>.md`에 저장되고, 출력(`## Output` 섹션, 없으면 보고서 전체)은 상태에 기록됩니다.
- 하위 노드의 프롬프트에는 `dependsOn`에 적힌 직접 의존 노드들의 출력(노드당 4,000자까지)과 전체 보고서 경로가 `<upstream_results>`로 자동으로 들어갑니다. 정의의 `goal`은 모든 노드에 전달됩니다.
- 메인 대화는 노드마다 출력 발췌가 담긴 짧은 진행 알림을 받고, 정착하면 모든 노드의 출력과 보고서 경로가 담긴 요약을 받습니다.
- 사용자가 `report.md`처럼 `REPORT*`, `SUMMARY*`, `FINDINGS*`, `ANALYSIS*` 이름의 파일을 요구하면 노드는 호스트가 서브에이전트의 쓰기를 거부하므로 전체 텍스트를 `## Output`에 돌려주고(또는 `<node-id>-notes.md`에 쓰고), 메인 대화가 정착 뒤에 그 내용을 해당 파일로 그대로 씁니다([강제](#강제)). 노드 id가 `report-draft`처럼 이 이름들로 시작하면 `<node-id>-notes.md`도 거부되므로 `notes-<node-id>.md`를 씁니다. lint 경고와 거부 메시지도 이 이름을 제안하며, 경고는 같은 경로를 여러 번 적어도 노드마다 한 번만 나옵니다.

**비대화형 세션에서 세션 유지**: 비대화형 세션(`claude -p` 등)에서는 메인 턴이 끝나도 이 세션의 실행이 `running`인 동안 플러그인이 그 턴의 `turn.complete`를 `sleep 1` 반복으로 붙잡아 세션을 열어 둡니다. 그런데 호스트는 붙잡힌 메인 턴을 끝난 뒤 60초까지만 기다립니다. 넘기면 `[WARN] headless session: turn events still running after 60000ms; the turn ends without them and their late notes are dropped`를 남기고, 그 뒤에는 살아 있는 노드 에이전트만 프로세스를 붙잡습니다. 그래서 메인 턴이 끝나고 60초가 지난 뒤에 노드가 끝나면 플러그인이 그 노드를 검증하거나 다음 노드를 띄우는 도중에 세션이 종료되어, 실행은 `running`, 노드는 `scheduled`나 `running`인 채 종료 코드 0으로 끝나곤 했습니다(백로그 B6). 이제 메인 턴이 붙잡힌 동안 노드 에이전트가 끝나면 플러그인이 검증보다 먼저 짧은 진행 프롬프트를 제출합니다. 노드가 끝났고 검증과 후속 실행은 백그라운드에서 이어진다고 알리며, 도구를 부르지 말고 한 줄로 답한 뒤 턴을 끝내라고 요청하는 내용입니다. 호스트가 이 프롬프트로 새 메인 턴을 시작하면 세션이 유지되고, 그 턴이 끝나면 플러그인은 실행이 정착할 때까지 다시 붙잡습니다. 비용은 노드가 끝날 때마다 메인 모델 턴이 짧게 한 번 더 도는 것입니다(그 프롬프트의 턴이 시작되기 전에 겹쳐 끝난 노드는 프롬프트 하나로 묶습니다). 이 턴의 한 줄 답변은 `claude -p`의 stdout에 그대로 나타납니다. 제출이 거부되거나 버려지면 `could not keep the session open for <run_id>/<node>`를 로그에 남깁니다. `claude -p "/dag run <파일>"`처럼 명령만 넘긴 세션에는 붙잡을 메인 턴이 아예 없어서, 첫 노드가 끝나는 순간 세션이 닫히고 후속 노드가 `no session is bound in this process`로 시작하지 못하곤 했습니다(2026-10-19 실측 14회 중 5회). 이제 비대화형 세션에서 메인 턴이 없을 때 `/dag run`·`retry`·`approve`가 실행을 시작하면, 플러그인이 "실행이 시작됐으니 한 줄로 답하고 턴을 끝내라"는 짧은 프롬프트를 제출해 메인 턴을 엽니다. 호스트가 명령 훅 안에서의 제출을 거부하므로 명령이 끝난 다음 틱에 제출하고, 그 턴이 끝나면 위와 같이 실행이 정착할 때까지 붙잡습니다. `turn.start`는 `agentId`가 있는 노드 에이전트의 턴에도 발생하므로, `agentId`가 없는 메인 루프의 `turn.start`만 메인 턴을 바쁨으로 표시합니다(2026-10-19 리허설에서 필요했던 수정입니다). 대화형 세션은 영향을 받지 않습니다.

**비대화형 세션의 도구 허용**: 비대화형 세션(`claude -p` 등)에서 DAG 노드 작업자의 도구 호출은 메인 대화와 같은 권한 설정을 따릅니다. 판정이 `ask`인 호출은 물어볼 상대가 없으므로 Claude Code가 거부합니다. 플러그인의 Jev 도구 승인이 `jev_confidence`(기본 `0.9`) 이상의 확신도로 허용을 고른 호출만 예외입니다. 2026-10-09에 `--allowedTools`에 Write가 빠진 `claude -p`로 실측했더니 Jev는 허용을 골랐지만 확신도가 0.88로 기준 0.9에 못 미쳐 노드의 Write가 거부됐습니다. 그래서 `claude -p`로 DAG를 돌릴 때는 노드가 쓰는 도구를 미리 허용하길 권합니다. 권장 명령은 `claude -p "<요청>" --allowedTools mcp__dag-workflow__dag Skill Read Write Edit Bash`입니다. `eval/run.ts`는 여기에 `TaskStop`, `ToolSearch`, `LSP`도 허용합니다. `--permission-mode acceptEdits`는 Write와 Edit만 덮고 Bash는 덮지 않으므로, Bash는 이 모드에서도 `--allowedTools`로 허용해야 합니다. 비대화형 세션에서 노드 작업자의 도구 호출이 `ask`로 남으면 플러그인은 판정을 그대로 두고(거부는 호스트가 합니다) 트랜스크립트에 한 줄을 `$.ui.log`로 남깁니다. `-p`나 SDK 호스트는 이 줄을 `ui_log`로 받고 디버그 로그에도 남으며, 같은 실행·노드·시도·도구에는 한 번만 남깁니다. 줄의 형식은 `<runId>/<nodeId>: <tool> needs approval that this non-interactive session cannot ask for (<why>); allow it up front with --allowedTools <tool> or a --permission-mode that covers it`입니다. `<why>`는 Jev가 왜 이 호출을 정하지 못했는지입니다. Jev가 답했지만 적용되지 않았으면 `Jev <outcome>: <choice> at <confidence>, jev_confidence <threshold>`(예: `Jev low-confidence: allow at 0.88, jev_confidence 0.9`), 답이 없었으면 `Jev <outcome>`(예: `Jev timeout`), 묻지 않았으면 `Jev not asked: jev_permission_scope is dag and the call carries no node task`입니다([Jev 를 활용한 자동 판단](#jev-를-활용한-자동-판단)의 승인 범위). 실행이 끝났을 때 플러그인이 올리는 완료 요약 메시지(메인 모델이 읽고 사용자에게 전하는 프롬프트)에도 같은 정보가 실립니다. 현재 시도에서 도구 호출이 `ask`로 남은 노드의 줄 끝에 `; needed approval this non-interactive session cannot give: <tools> (allow them up front with --allowedTools)`가 붙고, `<tools>`는 그 도구를 처음 나온 순서대로 `, `로 이은 목록입니다. 재시도한 시도는 이 목록을 처음부터 다시 만듭니다. 그래서 로그 줄이 보이지 않는 환경에서도 메인 모델이 해결 방법을 사용자에게 전할 수 있습니다. 노드 작업자의 도구 승인 판단 기록(`/dag decisions`, 도구 액션 `decisions`)에는 `runId`와 `nodeId`가 들어가고, 이 비대화형 경우에는 `<runId>/<nodeId>: ` 접두사를 뺀 같은 문장이 `note`로 붙습니다. 다만 `Jev not asked`인 경우(`jev_permission_scope`가 `dag`인데 호출에 노드 작업이 없을 때)는 Jev를 묻지 않으므로 판단 기록을 쓰지 않고, 그래서 `note`도 없습니다. 이 경우에는 로그 줄과 완료 요약의 힌트만 남습니다. 대화형 세션과 메인 대화의 호출에는 이 줄도, 요약 힌트도, `note`도 없습니다.

## 정의 형식

```yaml
key: review-fan-in          # 멱등 키: 같은 키+같은 정의로 다시 시작하면 기존 실행을 돌려줌
name: Integration review
goal: Find and confirm wiring bugs before the release
nodes:
  - id: navigation
    category: trivial
    prompt: Audit src/navigation for dead routes. Write findings to notes/navigation.md.
    writes: [notes/navigation.md]
    verify:
      - kind: file
        path: notes/navigation.md
        contains: "## Dead routes"
  - id: gate-wiring
    prompt: |
      Check that every feature gate in src/gates is wired.
      Write findings to notes/gates.md.
    writes: [notes/gates.md]
    verify:
      - kind: file
        path: notes/gates.md
        contains: "## Unwired gates"
  - id: verify
    category: standard
    dependsOn: [navigation, gate-wiring]
    prompt: Read notes/*.md, verify each finding against the code, and write the verdict to notes/verdict.md.
    writes: [notes/verdict.md]
    verify:
      - kind: file
        path: notes/verdict.md
        contains: "Verdict:"
      - kind: command
        argv: [npm, test]
```


| 필드                                     | 설명                                                                                                                                                                                |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                   | 1-64자의 영문, 숫자, `_`, `-`, `.`                                                                                                                                                      |
| `prompt`                               | 혼자 읽어도 이해되는 작업 지시                                                                                                                                                                 |
| `goal` (정의 수준)                         | 전체 목표. 모든 노드 프롬프트에 들어갑니다                                                                                                                                                          |
| `dependsOn`                            | 먼저 완료돼야 하는 노드 id. 이 노드들의 출력이 프롬프트에 자동으로 들어갑니다                                                                                                                                     |
| `category`                             | 모델 라우팅: `trivial`/`standard`/`debugging`/`writing`/`frontend`=sonnet, `hard`/`reasoning`/`creative`/`crux`/`architect`=opus. 생략하거나 미등록 값이면 sonnet |
| `agent`                                | 서브에이전트 타입(예: `Explore`). 기본값 `general-purpose`. 모델을 강제로 상속하는 `fork`는 Sonnet 하한을 보장할 수 없어 거부                                                                                       |
| `label`, `task_summary`, `description` | 패널 표시용                                                                                                                                                                            |
| `load_skills`                          | 노드가 시작 전에 불러올 스킬 이름                                                                                                                                                               |
| `verify`                               | **`start`·`amend`에서 필수.** 런타임이 직접 실행할 검사 1-16개. 파일 검사(`contains`/`absent`/`matches`/`lastLine`/`equals`)와 명령 검사(`expect`)의 문법은 [검증](#검증)                                                                                                                         |
| `writes`                               | 이 노드가 쓸 프로젝트 상대 경로나 폴더. 다른 세션과 겹치는지 보여 주는 데만 쓰고, 쓰기를 막지는 않습니다                                                                                                                     |
| `external`                             | 이 노드가 프로젝트 파일 밖을 바꾸면 `true`(push, 배포, DB·스토리지·설정 변경, 메시지 전송). 자동 리뷰 수정 라운드는 이런 노드를 다시 실행하지 않습니다 |
| `review` (정의 수준)                      | `{request, notes?, category?, rules?, security?}`. 선언하면 파싱할 때 `review-spec`과 `review-standards` 노드로 확장하고, `security`가 있으면 보안 관점 노드 7개와 `review-security`도 만듭니다. `request`는 사용자의 요청 문장으로, `review-spec` 프롬프트에 그대로 붙여 넣습니다. 이 id로 노드를 직접 정의하면 안 됩니다. 자세한 내용은 [검토와 커밋 단계](#검토와-커밋-단계) |
| `commit` (정의 수준)                      | `[{message, paths}]`. 선언하면 파싱할 때 노드 `commit`으로 확장합니다. 항목마다 `paths`만 스테이징해 `message`로 순서대로 커밋하며, 다른 변경은 스테이징하지 않고 푸시하지 않습니다 |


YAML은 DAG 정의에 필요한 부분집합만 지원합니다(매핑, 시퀀스, 인용 문자열, `[a, b]`, `|`/`>` 블록 스칼라, 주석). `{a: 1}` 형태의 플로우 매핑은 지원하지 않습니다.

정의 수준 `review`와 `commit`은 이렇게 씁니다. 노드는 사용자가 만든 것만 적고, 검토 노드와 커밋 노드는 플러그인이 만듭니다.

```yaml
key: csv-export
goal: Add CSV export to the report page
nodes:
  - id: export
    prompt: "TASK: Add src/export.ts and tests/export.test.ts. STOP WHEN: the export test passes."
    writes: [src/export.ts, tests/export.test.ts]
    verify:
      - kind: command
        argv: [bun, test, tests/export.test.ts]
review:
  request: "Add CSV export to the report page"   # 사용자의 요청 문장. review-spec에 그대로 들어감
  category: standard                             # 생략하면 standard
commit:
  - message: "feat(export): add CSV export"
    paths: [src/export.ts, tests/export.test.ts]
```

카테고리 제안 기준은 `skills/planning/references/planning.md`의 **Category routing**에 있습니다. DAG를 작성하는 메인 Claude가 값을 제안하며, 사용자가 정의 파일을 작성하면 그 값이 제안이 됩니다. Jev가 켜져 있으면 `hooks/engine/jev.ts`의 분류 기준으로 작업 내용을 독립적으로 평가하고, 확신도가 기준 이상일 때 실행 카테고리를 바꿉니다. 최종 감사가 제안이나 Jev 판단으로 `trivial`이 되면 Jev 설정과 관계없이 `standard`로 실행합니다(판단 주체 `rule`). 최종 모델은 `hooks/engine/node-prompt.ts`의 매핑으로 정합니다. `trivial`과 `standard`는 모두 Sonnet이지만 기계적 작업과 판단 작업을 구분하는 이름입니다. 작업자 모델은 최소 Sonnet이며, 세션이나 에이전트 타입의 Haiku 설정을 상속하지 않도록 모델을 명시합니다.

## Jev 를 활용한 자동 판단

Claude Code를 시작하는 환경에 `TYPESAFE_API_KEY`가 있으면 TypeSafe API를 기본 판단 경로로 씁니다. 키는 저장소나 체크포인트에 저장하지 않습니다. 키를 추가한 뒤에는 새 세션을 시작하거나 `/reload-plugins`를 실행합니다.

`jev_model_fallback`(기본 `true`)이 켜져 있으면, 키가 없거나 TypeSafe 요청이 실패·시간 초과·2xx 외 상태로 끝날 때 같은 질문과 기준을 세션의 Sonnet 모델(`$.model.complete`, effort `low`, 요청마다 10초 제한)에 보냅니다. 따라서 키가 없어도 Jev는 활성 상태입니다. 이 대체 호출은 현재 Claude Code 로그인으로 실행되므로 **사용량이 사용자의 Claude 요금제(구독 한도 또는 API 과금)에 포함됩니다**. 응답은 각 질문의 선택지·확신도와 가능성이 높은 선택지 3개의 확률을 담은 JSON이어야 하며, 형식이 틀리거나 선택지 밖이거나 확신도가 범위를 벗어난 답은 버립니다. 같은 `jev_confidence` 기준과 적용 규칙을 따르고, 모델이 답하지 못하거나(중단·API 오류·빈 응답) 호출이 실패하면 기존 흐름을 유지합니다. 키가 있는 정상 응답(형식이 틀린 2xx 응답 포함)에는 대체 호출을 하지 않습니다.

- **작업 배정:** `start` 전에 노드별 카테고리 질문을 한 번의 TypeSafe 요청으로 보냅니다. 세션 모델은 답을 통째로 돌려줘서 질문이 많을수록 느려지므로, 노드를 최대 8개 요청에 고르게 나눠 동시에 보냅니다(노드가 8개 이하면 노드마다 요청 하나). 이때 판단 기록의 결과와 지연 시간은 노드마다 따로 남습니다. 세션 모델이 고른 카테고리는 `jev_model_routing_confidence`(기본 `0.8`) 이상이면 적용합니다. 실측한 답 117개에서 고른 카테고리는 모두 맞았지만 확신도가 0.60–0.97로 흩어져, 기준 0.9에서는 맞는 답의 28%가 버려졌기 때문입니다. 도구 승인과 복구 판단은 계속 `jev_confidence`를 씁니다. `amend`는 재실행 대상만, `retry`는 재실행할 노드와 변경된 프롬프트를 평가합니다. 확신도가 낮거나 평가가 실패하면 제안 카테고리를 유지합니다. 동일 정의의 재사용은 재평가하지 않습니다.
- **도구 승인:** 기존 권한 판정이 `ask`인 호출만 평가합니다. 사람에게 묻는 도구(`AskUserQuestion`, `ExitPlanMode`)는 평가하지 않습니다. 훅의 `allow`가 그 창을 닫지 못해서, 질문마다 Jev를 부르면 기다림만 늘고 바꿀 수 있는 것은 사용자의 질문을 거부하는 것뿐이기 때문입니다. 확신도 높은 `allow`는 자동 실행, `deny`는 거부로 바꿉니다. `ask`·낮은 확신도·오류는 기존 판정의 이유와 규칙까지 그대로 유지합니다. 이미 내려진 `allow`와 `deny`, strict(와 `auto`의 DAG 턴)의 메인 도구 제한은 바꾸지 않습니다.
- **승인 범위:** `jev_permission_scope`가 `dag`(기본)이면 DAG 노드 작업자가 호출한 도구만 평가하고, 메인 대화의 `ask`는 Jev 요청도 판단 기록도 없이 기존 판정 그대로 둡니다. `all`이면 모든 `ask` 판정을 평가합니다. 노드 문맥은 작업자의 도구 호출 이벤트로 연결되는데, 첫 웨이브 뒤에 시작된 작업자는 이 이벤트가 mod에 오지 않으므로`dag`에서는 그 작업자의 `ask`도 평가하지 않고 기존 확인 창으로 남깁니다. 노드 작업자의 도구 승인 판단 기록에는 `runId`와 `nodeId`가 들어가고, 비대화형 세션에서는 Jev가 정하지 못한 이유를 적은 `note`도 붙습니다([결과 전달](#결과-전달)의 **비대화형 세션의 도구 허용** 문단).
- **실행 방식(`mode`):** `enforcement`가 `auto`일 때만 씁니다. 사용자 프롬프트마다 `direct`(메인 대화에서 직접 실행)와 `dag` 중 하나를 고르는 질문을 한 번 보냅니다([강제](#강제)). `dag`는 노드가 셋 이상 필요하고 병렬 또는 격리 실행으로 시간이나 컨텍스트를 아낄 때만 고르고, 질문·설명·단일 파일 수정처럼 한두 단계로 끝나는 요청은 `direct`입니다. 확신도 기준은 `0.8`로 고정이고 TypeSafe와 세션 모델에 같은 값을 씁니다(`jev_confidence`, `jev_model_routing_confidence`와 무관). 실행 방식이 틀려도 잃는 것은 안전이 아니라 시간이고, 직접 실행 턴도 사용자의 평소 권한 규칙을 지나기 때문에 도구 승인보다 낮게 잡았습니다. 확신도 `0.8` 이상의 `dag`만 DAG 턴(`strict` 규칙)을 만들며, 그 밖에는 모두 직접 실행 턴입니다(`direct` 판단, 낮은 확신도, 키도 세션 모델 대체도 없는 경우, 제한 시간 초과, 잘못된 응답). 이 세션에 정착하지 않은 실행이 있거나 `jev_enabled`가 꺼졌거나 쓸 수 있는 경로가 없으면 Jev를 부르지 않고 기록도 남기지 않습니다. 키가 없으면 사용자 프롬프트마다 세션 모델(Sonnet, effort `low`)을 한 번 부르므로 그 사용량이 사용자의 Claude 요금제에 포함됩니다. `/dag decisions`와 패널의 Decisions 탭에는 종류 `mode`(한국어 패널은 **실행 방식**), 대상 `request`(직접 실행 턴에서 선택 창에 답했을 때의 판단은 대상 `answer`), 제안값 `direct`, 선택값 `direct` 또는 `dag`로 나타납니다.
- **표시 방식(`surface`):** `enforcement`가 `auto`이고 실행 방식을 묻는 프롬프트에만 같은 요청에 실리는 두 번째 질문입니다. 답을 `chat`과 `board` 중 어디에 보여 줄지 고르며, 확신도 `0.8` 이상의 `board`만 적용하고 그 밖에는 채팅입니다. 조건과 동작은 [표시 방식 판단](#표시-방식-판단)에 있습니다.
- **판단 입력:** 배정에는 실행 목표·노드 작업·의존 ID·제안 카테고리를 보냅니다. 세션 모델에는 제안 카테고리를 빼고, 그 노드에 의존하는 노드 ID(`dependents`)를 더해 보냅니다. 제안이 틀리면 모델의 답은 맞아도 확신도가 기준 아래로 떨어지는 것이 실측됐기 때문입니다. `dependents`는 노드별로 나눠 물을 때 사라지는 그래프 정보로, 최종 감사(의존하는 노드가 없고 입력이 둘 이상인 검증 노드)를 알아보는 데 씁니다. 승인에는 도구 이름·인자·현재 사용자 요청·프로젝트 경로와, 연결 가능한 경우 해당 노드의 목표·작업을 보냅니다. 실행 방식에는 사용자 요청(4,000자까지)과, "예"나 "1" 같은 짧은 답을 풀이할 맥락으로 직전 사용자 요청 최대 3개(각 500자까지), 그 요청 앞의 어시스턴트의 직전 답변 마지막 1,000자를 보냅니다. 짧은 답은 길이가 아니라 그 답변에서 고르는 선택지나 계획으로 판단하며, 대화 기록을 읽을 수 없으면 직전 답변 없이 묻습니다. 선택 창 답에는 사용자 요청과 어시스턴트의 직전 답변 대신 고른 답과, 질문 및 그 선택지를 보내고(비밀값은 같은 방식으로 가립니다) 직전 사용자 요청 최대 3개는 그대로 함께 보냅니다. 이 데이터는 TypeSafe의 외부 API로 전송됩니다.
- **승인 입력 마스킹:** 보내기 전에 도구 인자의 비밀값(키, 토큰 등)은 `[REDACTED:<종류>]`로 바꿉니다. 실행 방식에 보내는 요청과 어시스턴트의 직전 답변의 비밀값도 같은 방식으로 가립니다. 요청은 앞부분을 남기지만, 직전 답변은 끝부분(마지막 1,000자)을 남깁니다. 2,000자를 넘는 문자열은 길이·해시·앞 1,000자만 보내고, 목표와 작업은 각각 2,000자까지, 요청 전체는 4,000자까지로 줄입니다.
- **확인:** `snapshot`의 `category`는 원래 제안이며, `routing`은 실제 선택한 카테고리·판단 주체(`jev`, `definition`, 최종 감사 규칙 `rule`)·Jev 확신도를 담습니다. `model`은 실제 시작된 작업자의 모델입니다. 터미널 로그에도 적용한 판단을 표시합니다. `/dag decisions`의 각 기록에는 판단 경로 `backend`(`http` 또는 세션 모델 `model`)가 붙으며, 이 필드가 없는 예전 기록도 그대로 읽습니다.
- **실패 처리:** 누락·잘못된 응답, HTTP 오류, 제한 시간(TypeSafe 5초, 세션 모델 10초) 안에 답이 없는 경우 모두 기존 배정·승인 흐름으로 돌아갑니다. `start`는 배정 판단을 기다린 뒤 반환하므로, 키가 없으면 최대 10초, 키가 있는데 TypeSafe가 답하지 않으면 최대 약 15초 늦어집니다. 도구 승인을 판단하는 동안에는 그 도구 호출도 같은 시간만큼 기다립니다. 실행 방식 판단은 두 경로를 합쳐 8초로 제한하며, 그동안 사용자 프롬프트가 기다리고 시간이 지나면 `strict` 규칙으로 진행합니다. 현재 mods HTTP API에는 요청 취소 옵션이 없어 시간 초과된 HTTP 요청 자체는 뒤에서 끝날 수 있지만, 늦은 응답으로 결정을 바꾸지는 않습니다.

TypeSafe 모델은 `jev-latest`를 사용합니다. 기본 확신도 `0.9`(세션 모델의 카테고리 배정과 실행 방식은 `0.8`)는 자동 적용 기준이며 정확도 보증이 아닙니다. `jev_enabled=false`이거나, 키가 없고 `jev_model_fallback=false`면 모델 호출 없이 기존 방식으로 동작하고(`auto`는 정착하지 않은 실행이 없는 한 모든 턴을 직접 실행) 시작 로그에 `Jev inactive`가 표시됩니다.

### Jev 호출 병합과 상한

동일한 세션·프로젝트·사용자 요청·판단 입력·질문 분할을 가진 진행 중 Jev 요청만 합칩니다. 각 호출의 판단 기록은 따로 남고, 한 호출의 취소가 다른 대기자를 취소하지 않습니다. 모든 대기자가 취소되면 공유 모델 요청도 중단합니다. mods HTTP API에는 취소 옵션이 없어 HTTP 요청은 뒤에서 끝날 수 있지만 그 결과를 취소된 호출에 적용하거나 모델 대체로 이어가지는 않습니다. 완료된 승인 결과는 캐시하지 않으며, 입력이나 작업 범위가 달라진 요청은 합치지 않습니다.

`jev_max_calls`는 로드된 세션의 실제 HTTP·모델 판단 호출을 합쳐 제한합니다(기본 `100`, 정수 `1–1000`). 실패한 HTTP 호출과 모델 대체의 분할 요청도 각각 한 번으로 세며, 진행 중 요청에 합류한 호출은 추가로 세지 않습니다. 상한 뒤에는 도구 권한의 원래 `ask`·이유·규칙, 카테고리 제안을 유지하고 자동 복구를 중단합니다. 판단 기록은 `outcome: disabled`, `note: budget-exhausted` 이유를 포함합니다. 이미 실행 중인 작업이나 선언된 검증을 취소하지 않습니다. 이 제한은 작업자 모델 사용량이나 실제 청구액의 상한이 아닙니다.

호출 수는 메모리에만 보관하고 새 세션 ID나 플러그인을 다시 로드할 때 초기화합니다. 같은 세션 ID의 `/clear`로는 상한을 다시 채우지 않습니다. 정수 범위 밖의 설정은 기본값을 유지합니다. 새 훅·감시 타이머·영구 승인 캐시는 추가하지 않습니다.

## 검증

`start`와 `amend`는 모든 노드에 `verify`가 있어야 받아들입니다. 하나라도 없으면 `verification_required`로 거부합니다. 형식이 틀리면 `invalid_verification`입니다.

검사는 파일 검사와 명령 검사 두 가지이고, 하나의 문법을 씁니다. 문구가 없어졌는지(`absent`), 판정 줄이 마지막에 있는지(`lastLine`), 실패해야 정상인 명령(`expect`)도 `sh -c` 같은 셸 래퍼 없이 검사 하나로 적습니다.

| 검사 | 형식 | 통과 조건 |
| --- | --- | --- |
| 파일 | `{kind: file, path, contains?, absent?, matches?, lastLine?, equals?}` | 경로가 있고, 준 텍스트 필드가 모두 성립 |
| 명령 | `{kind: command, argv: [...], expect?}` | 프로젝트 루트에서 셸 없이 실행해 30초 안에 끝나고 `expect`를 만족. `expect`가 없으면 종료 코드 0 |

텍스트 필드는 파일 검사와, 명령 검사의 `expect.stdout`·`expect.stderr`가 똑같이 씁니다. 여러 개를 함께 주면 모두 성립해야 통과합니다.

| 텍스트 필드 | 통과 조건 |
| --- | --- |
| `contains` | 그 문자열이 들어 있음(빈 문자열 불가) |
| `absent` | 그 문자열이 없음 |
| `matches` | 자바스크립트 정규식이 텍스트에서 일치. 여러 줄 모드라서 `^`와 `$`가 줄마다 맞음. 다른 정규식 문법(`\A`, `\Z`, `\z`, `\p{L}`, `[[:digit:]]` 등)은 자바스크립트에서 오류 없이 평범한 글자로 읽혀 절대 통과하지 않으므로 `invalid_verification`으로 거부합니다. 텍스트 맨 앞은 `(?<![\s\S])`, 맨 끝은 `(?![\s\S])`로 씁니다 |
| `lastLine` | 끝의 공백을 지운 텍스트의 마지막 줄이 이 문자열과 같음 |
| `equals` | 끝의 공백을 지운 전체 텍스트가 이 문자열과 같음 |

`lastLine`과 `equals`는 텍스트 끝의 공백과 줄바꿈만 지우고 앞쪽 공백은 그대로 비교합니다. `contains`, `absent`, `matches`는 텍스트를 그대로 봅니다.

**파일 검사의 경로**

- `path`는 프로젝트 상대 경로입니다. 프로젝트 밖의 파일은 절대 경로로 읽기만 하는 검사에 한해 확인할 수 있어서, 노드가 `/tmp`에 남긴 노트 파일의 판정 줄도 볼 수 있습니다. 절대 경로에는 `C:/notes.md` 같은 윈도 경로도 쓸 수 있습니다. 어느 경로든 `..`과 NUL 문자는 거부합니다. 상대 경로에는 대소문자와 관계없이 `.claude` 구간이 들어갈 수 없고, 절대 경로는 읽기 전용이며 `.claude/dag`에 닿을 수 없습니다. `writes`는 이전처럼 프로젝트 상대 경로만 받으며, 절대 경로(윈도 드라이브 문자 포함), `..`, `.claude` 안쪽 경로를 거부합니다.
- 경로가 없으면 `absent`를 줬어도 실패합니다. 없는 경로에서 "문구가 없다"를 통과시키지 않습니다.
- 폴더 경로에는 `contains`와 `absent`만 쓸 수 있습니다. 폴더 아래의 모든 일반 파일(숨김 파일과 gitignore 대상 포함)에 적용하고, 최대 2,000개 파일·20MB까지 읽습니다. `contains`는 파일 중 하나라도 그 문자열을 가지면 통과하고(모든 파일이 가질 필요는 없음), `absent`는 어느 파일에도 그 문자열이 없어야 통과합니다. 폴더를 훑을 때 프로젝트 자신의 `.claude/dag`(런의 체크포인트)는 건너뜁니다. 체크포인트에는 정의에 적은 검사 문구가 그대로 들어 있어서, 읽으면 `contains`가 저절로 통과하기 때문입니다.

**명령 검사의 `expect`**

- 형식은 `{exit?, stdout?, stderr?}`입니다. `exit`는 숫자 하나이거나 숫자 배열이고, 종료 코드가 거기에 들어 있어야 통과합니다. `exit`를 주지 않으면 종료 코드 0만 통과합니다.
- `stdout`과 `stderr`에는 위 텍스트 필드를 씁니다.
- 프로그램이 시작되지 못하거나(없는 프로그램, 권한 오류) 30초 제한을 넘기면 `expect`에 무엇을 적었든 실패입니다.
- 명령은 Claude Code 프로세스의 PATH로 셸 프로필 없이 실행됩니다. 그래서 `start`·`amend`·dry run·`/dag preview`는 노드를 띄우기 전에 `argv[0]`과 `sh -c`/`bash -c` 스크립트 안의 명령 이름을 그 PATH에서 찾아보고, 없는 프로그램이 있으면 `invalid_verification`으로 거부합니다. Claude의 Bash 도구에는 있는 `rg` 같은 프로그램이 이 환경에는 없을 수 있기 때문입니다. `./run.sh`처럼 경로로 부른 프로그램, 로그인 셸(`-l`), here-document·`case`·`source`·`PATH=` 등 해석하지 않는 구문이 있는 스크립트는 찾아보지 않습니다.

예시입니다. 첫 검사는 폴더 전체에서 지운 옵션 이름이 남지 않았는지, 둘째는 `/tmp`의 노트 파일 마지막 줄이 판정 줄인지, 셋째는 잘못된 입력을 넣었을 때 종료 코드 1로 끝나며 이유를 stderr에 적는지 확인합니다.

```yaml
verify:
  - kind: file
    path: skills                    # 폴더: contains와 absent만 가능
    absent: "legacy_mode"
  - kind: file
    path: /tmp/review-notes.md      # 프로젝트 밖은 절대 경로, 읽기 전용
    lastLine: "Verdict: PASS"
  - kind: command
    argv: [node, tools/lint.js, fixtures/bad.json]
    expect:
      exit: 1                       # 실패해야 정상. 여러 코드는 [1, 2]
      stderr:
        contains: "unknown field"
```

`dag` 도구에 JSON 정의로 넘길 때 같은 명령 검사는 다음과 같습니다.

```json
{"kind": "command", "argv": ["node", "tools/lint.js", "fixtures/bad.json"], "expect": {"exit": 1, "stderr": {"contains": "unknown field"}}}
```

- 노드 에이전트가 완료를 보고하면 런타임이 검사를 모두 실행하고, 시도마다 `.claude/dag/runs/<run_id>/<node>.verification.<시도>.json`에 증거(검사, 통과 여부, 종료 코드, 출력 4,000자까지)를 남긴 다음에야 `completed`로 바꿉니다.
- 검사가 하나라도 실패하거나 증거가 없으면 노드는 `failed`가 되고 하위 노드는 시작하지 않습니다.
- 새 검사 증거에는 `outcome`을 기록합니다. `passed`는 기대 충족, `failed`는 확인한 결과의 기대 불충족(산출물 경로 없음 포함), `not_run`은 명령 시작 실패·시간 초과로 완료 결과를 얻지 못함, `unknown`은 읽기 권한 오류·검사 범위 제한·기대 출력 잘림 등으로 판정 불가입니다. 종료 코드가 이미 기대와 다르면 출력이 잘려도 `failed`입니다. `not_run`과 `unknown`도 완료를 막으며, 완료 요약과 세션 복원에 검사별 결과가 전달됩니다.
- 기존 `passed` 필드는 유지합니다. `outcome`이 없는 예전 기록은 `passed: true`만 통과로 읽고, `false`는 실패와 검사 불가를 구별할 근거가 없어 `unknown`으로 표시합니다. 기존 실행의 완료 상태를 바꾸거나 자동으로 재실행하지 않습니다.
- 상태의 의미와 대응 지침은 계획 스킬뿐 아니라 완료 알림, `snapshot`의 `verification_guidance`, 세션 복원 컨텍스트와 작업자 프롬프트에도 전달됩니다. `failed`면 검사·`detail`·종료 코드를 읽고 산출물 또는 잘못된 검사를 고칩니다. `not_run`이면 실행 프로그램·전제 조건·시간 제한을 먼저 확인하고, `unknown`이면 읽기 권한·출력 잘림·검사 범위 등 부족한 근거를 먼저 해결합니다. 상태 이름만으로 코드 결함이라고 판단하거나 검사를 약화하지 않습니다. 자동 복구 작업자에게는 이전 시도의 검사별 결과, 상세 이유의 앞 240자와 전체 증거 경로도 전달됩니다.
- 검증은 **적어 둔 검사가 통과했다는 것만** 증명합니다. 결과가 의미상 모두 옳다는 보증은 아닙니다. 그래서 검사는 산출물의 핵심을 실제로 확인하도록 고르고, `true` 같은 빈 검사나 텍스트 필드 없는 파일 검사는 쓰지 않습니다.
- `verify`가 없는 예전 완료 기록은 미검증 상태로 표시하며, 이미 끝난 작업을 자동으로 다시 실행하지 않습니다. 예전 노드를 다시 실행할 때 계약이 없으면 "검증 계약 없음"으로 실패하고 자동 복구도 하지 않습니다. 정의에 `verify`를 넣어 `amend`하거나 새로 `start`합니다. 동일 정의의 멱등 재사용은 기존 기록의 검증 상태를 그대로 돌려줍니다.

### 빈 검증 경고

통과는 하지만 산출물이 옳다는 것을 거의 증명하지 못하는 검사는 정의 린트가 경고합니다. 경고 문구는 `node "<id>": vacuous verify - check 1 ...`로 시작하고, `start`와 `amend`가 돌려주는 `warnings`에 담기며 `/dag run`은 `Warnings:` 아래에 보여 줍니다. 경고일 뿐이라 실행을 거부하지는 않습니다. 노드마다 경고는 하나이고, 문제가 있는 검사를 `verify` 안의 위치(1부터 셈)로 모두 나열합니다. 한 검사에는 아래 규칙 중 먼저 맞는 하나만 적용합니다.


| 규칙  | 조건                                                                                     | 이유                                        |
| --- | -------------------------------------------------------------------------------------- | ----------------------------------------- |
| V1  | 텍스트 필드(`contains`, `absent`, `matches`, `lastLine`, `equals`)가 하나도 없는 파일 검사 | 파일이 있다는 것만 증명합니다. `touch`로 만든 빈 파일도 통과합니다 |
| V2  | 명령의 프로그램(`argv[0]`의 마지막 경로 이름)이 `true`, `:`, `echo`, `printf`, `exit`, `yes`, `sleep`  | 인자와 관계없이 항상 통과합니다                         |
| V3  | `test` 또는 `[`의 `-` 인자가 하나 이상이고 모두 `-e`, `-f`, `-d`, `-s`이거나, 프로그램이 `ls`, `stat`, `cat` | 경로가 있다는 것만 증명합니다                          |
| V4  | 종료 코드를 둘 이상 허용(`expect.exit` 배열)하면서 `stdout`·`stderr`를 확인하지 않는 명령 | 허용한 종료 코드 어느 쪽으로 끝나도 통과해서, 출력이 틀려도 걸러내지 못합니다 |


`test -n`, `test -r`, `test -z`처럼 다른 연산자가 하나라도 있거나 `-` 인자가 없는 `test a = b`는 경고하지 않습니다. `/bin/true`처럼 경로가 붙어도 마지막 이름으로 판단합니다.

대신 산출물의 핵심 문구를 `contains`에 적은 파일 검사, 사라져야 할 문구를 `absent`에 적은 파일 검사, 판정 줄을 `lastLine`으로 확인하는 파일 검사를 쓰거나, 산출물이 틀리면 종료 코드가 달라지는 명령(테스트 실행, `grep -q '<문구>' <파일>` 등)을 씁니다. 실패해야 정상인 명령은 `expect.exit`에 기대하는 종료 코드와 `stderr`·`stdout` 필드를 함께 적습니다.

검증 노드를 알아보는 경고(검증 노드 없음, 최종 감사 판정)는 id·label·요약에서 verify/validate/check/test/review/audit로 **시작하는 단어**만 검증 노드로 봅니다. `preview`처럼 단어 중간에 `review` 같은 글자가 들어 있는 경우는 세지 않습니다.

한계: 린트는 프로그램 이름과 위 플래그만 봅니다. `sh -c '...'` 같은 셸 래퍼는 분석하지 않으므로 그 안에 `true`나 `touch`를 넣어도 경고가 나오지 않습니다.

### 검토와 커밋 단계

두 축 검토 한 쌍과 커밋 노드는 모든 코드 변경 실행에 같은 모양으로 들어가므로, 손으로 쓰지 않고 정의 수준의 `review`와 `commit` 필드로 선언합니다. 플러그인이 정의를 파싱할 때(`start`, `amend`, `/dag run`, 드라이런) 이 필드를 노드로 확장하고, 그 노드의 검사도 [검증](#검증)의 검사 문법으로 만들어 붙입니다. 프롬프트는 템플릿입니다. 드라이런(`start {dryRun: true}`)의 `preview`에는 확장된 노드가 보입니다.

- `review: {request, notes?, category?, rules?, security?}`: 노드 `review-spec`과 `review-standards`를 만듭니다. 둘 다 사용자 노드 전부에 의존하고 서로는 의존하지 않습니다. `request`는 사용자의 요청 문장이며 `review-spec` 프롬프트에만 그대로 붙여 넣습니다(`review-standards` 프롬프트에는 요청을 넣지 않습니다). 두 검토 노드는 파싱할 때 커밋 해시를 받지 않고, 실행하면서 직접 `git rev-parse HEAD`를 실행해 기준점을 고정합니다. `category`를 생략하면 `standard`입니다. 검토 노트는 `notes`가 없으면 `/tmp/dag-review/<안전하지 않은 문자를 바꾼 key>-<key의 6자리 16진수 해시>/`에 씁니다. 검증은 노트의 마지막 줄이 `Spec verdict: PASS`(`review-spec`)와 `Standards verdict: PASS`(`review-standards`)인지 `lastLine`으로 확인합니다. 플러그인은 생성된 검토 노드를 시도하기 전에 그 노트 파일을 먼저 지우므로, 이전 시도나 다른 실행이 남긴 오래된 판정으로는 통과하지 못합니다. 검토는 크리티컬 패스 끝에 있으므로 템플릿이 범위를 정해 둡니다. 노트는 항목마다 한 줄로 쓰고 출력은 결정적인 줄만 인용합니다. `review-spec`은 선언된 검사 외에 직접 만든 probe를 두 개까지만 실행하고(안전하지만 틀린 산출물 점검표의 2·3번), 검증 스크립트·테스트 하네스·mutant를 만들지 않습니다. 2026-10-10 eval에서 최종 감사 노드는 150-230초, 생산 노드는 5-30초였고, 감사 하나는 직접 만든 검증 스크립트와 mutant에 약 95초를 썼습니다. `rules`는 `review-standards`가 먼저 읽을 저장소 규칙 파일의 경로 목록입니다. 이 노드는 목록과 별개로 저장소 루트와 변경이 닿는 폴더에서 CONTRIBUTING, CLAUDE.md, AGENTS.md 같은 규칙 파일도 스스로 찾아 읽습니다. `security`는 아래 [보안 검토 (선택)](#보안-검토-선택)에 있습니다.
- `commit: [{message, paths}]`: 노드 `commit`을 만듭니다. `review`가 있으면 검토 노드(`security`가 있으면 세 개, 없으면 두 개) 뒤에, 없으면 모든 사용자 노드 뒤에 실행합니다. 항목마다 그 `paths`만 스테이징해 `message`로 순서대로 커밋하고, 다른 변경은 스테이징하지 않으며 푸시하지 않습니다. 검증은 세 가지입니다. 커밋마다 `git log --format=%s`의 제목이 `message`의 첫 줄(제목)과 같은지만 비교하고(본문은 비교하지 않습니다), 나열한 `paths`가 모두 커밋됐는지(`git status --porcelain -- <paths>`가 비었는지) 확인하며, 각 커밋이 자기 `paths` 밖의 파일을 하나도 바꾸지 않았는지 확인합니다. 마지막 검사가 `git add -A` 같은 넓은 스테이징으로 관련 없는 변경이 커밋에 섞이는 것을 막습니다.

`review-spec`, `review-standards`, `commit` id로 노드를 직접 정의하면 안 됩니다. `security`가 있으면 `review-security`, `security-<관점>`, `security-verify-`로 시작하는 id도 마찬가지입니다. `amend`에는 원래 `review`와 `commit` 필드를 다시 담아 보냅니다.

`review-spec`은 테스트와 검사·권한 정책이 약해져서 통과한 것은 아닌지도 고정한 HEAD와 비교합니다. 테스트 삭제, skip/todo/only 추가, 단언·모의 객체 약화, 테스트 검색 범위 축소, 린트·타입·보안·검증·권한 설정 완화를 `## Real check`에 파일·줄, 잃은 동작이나 통제, 요청에 근거한 변경 이유와 대체 검증 근거로 기록합니다. 바뀐 요구사항의 테스트 수정, 동등한 커버리지 이동, 문구만 고정하던 단언 제거는 자동 실패가 아닙니다. 동작 보존 근거가 없거나 요청과 무관하게 정책을 우회하면 `## Findings`의 (c)에 적어 기존 `Spec verdict: FAIL` 판정과 수정 라운드를 적용합니다. 코드 작성 노드도 같은 변경 이유와 근거를 `## Output`에 남깁니다.

`review.request`는 파싱할 때 경고 두 가지를 더 냅니다. 첫째, 요청의 절이 결과물을 이름 붙이면서 관찰 가능한 기준(반환값·출력, 오류와 경계 사례를 뜻하는 상태 코드나 `returns`·`when`·`prints` 같은 동사, 따옴표로 묶은 리터럴)이 없을 때입니다. 백틱으로 감싼 이름만으로는 기준이 되지 않습니다. `review-spec`이 그런 부분을 자기 해석으로 판정해 같은 실행도 판정이 갈리므로, 결과물마다 기대 동작을 적습니다. 키트의 "Add a user search endpoint"가 이 경고에 걸리는 예이고, 무엇을 돌려주는지와 오류·빈 결과를 함께 적으면 사라집니다. 둘째, `review.security`가 있고 요청이나 목표가 엔드포인트·라우트·API·URL·웹·서버·페이지·폼 같은 네트워크 표면을 말하는데, 둘 다 누가 무엇을 쓸 수 있는지는 말하지 않을 때입니다. 보안 수정이 접근 검사를 넣으면 `review-spec`이 그것을 요청하지 않은 변경이나 요청한 결과(요청한 404 대신 403)와의 충돌로 보고할 수 있으므로, 작업마다 누가 수행할 수 있는지 적습니다.

#### 의미 없는 코드 차단 (anti-slop)

추가 검토 후보 두 가지는 자동 위반 판정이 아닙니다. `test-expectation-change`는 이름이 유일한 TS·JS 테스트의 동일 `expect` 표현식·matcher에서 기대 리터럴만 바뀐 경우를 안내합니다. 숫자·불리언·null·undefined·이스케이프 없는 문자열을 비교하며, 동등한 리터럴 표기나 모호한 대응 관계는 제외합니다. `requirement-substitution`은 최신 사용자 요청에 실제 API 연동이 명시되어 있는데, production의 동일한 최상위 named 함수가 직접 반환하던 `fetch`를 고정 응답으로 바꾼 경우를 안내합니다. 한국어·영어의 명시 요청을 지원하고, 테스트·mock·fixture 경로, 부정된 요청, 일반 테스트 mock은 제외합니다. 임의 SDK·별칭·복잡한 제어 흐름은 추정하지 않습니다. 두 후보 모두 기존 skip·저장소 예외를 따르며, 정당한 요구사항 변경이나 동등한 검증 근거가 있으면 변경을 유지할 수 있습니다. 경고만으로 rollback이나 FAIL 판정을 하지 않습니다.

기존 Edit/Write 스캔에는 TS·JS의 `.test`/`.spec` 파일을 수정 전후로 비교하는 테스트 약화 경고도 있습니다. `test-skip`은 새 skip/todo·상수 실행 비활성화, `test-disabled`는 같은 이름의 테스트를 빈 본문이나 즉시 return으로 바꾸는 경우, `test-tautology`는 의미 있는 단언을 상수끼리의 항상 참인 단언으로 바꾸는 경우를 안내합니다. 빈 본문으로 만드는 삭제만 있는 수정도 비교합니다. 단언 개수 감소, 정상적인 통합·이름 변경, 주석·문자열 예제만으로는 경고하지 않습니다. 인식하는 형태가 제한되어 모든 테스트 약화를 잡는 것은 아니며, 기존 `anti_slop_scan`, `anti_slop_skip`, 저장소의 `anti-slop allow:` 예외를 그대로 따릅니다. 경고는 수정을 거부하거나 검증 결과를 바꾸지 않습니다.

`skills/anti-slop/`은 지워도 동작이 그대로인 코드와, 코드가 이미 아는 타입 정보를 버리는 코드를 막는 규율입니다. 모든 언어에 적용하고 예시는 TS·JS·Python·Go·Java·Rust·Ruby로 듭니다. 세 겹으로 동작합니다.

1. 스캔: Edit이나 Write가 끝나면 플러그인이 그 호출이 추가한 줄만 정규식으로 검사하고, 걸린 패턴을 도구 결과 뒤에 모델이 읽는 컨텍스트로 붙입니다. 메인 대화와 DAG 노드 모두에 적용되고 모델 호출이 없습니다. 모양만 보므로 예외에 해당하면 모델이 그 예외를 밝히고 코드를 남깁니다. `anti_slop_scan`으로 끄고 `anti_slop_skip`으로 패턴을 뺍니다. 저장소 하나에서만 빼려면 루트의 `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md` 중 하나에 `anti-slop allow: <패턴 id>, ...` 줄을 쓰고 이유를 함께 적습니다. 프로젝트 `.claude/settings.json`의 `pluginConfigs`는 플러그인에 전달되지 않습니다(2026-10-12 측정, `--settings` 파일은 전달됨).
2. 작성: 계획 스킬은 코드를 쓰거나 고치는 노드의 `load_skills`에 `dag-workflow:anti-slop`을 넣습니다. 노드는 보고하기 전에 자기 diff를 목록 전체와 대조해 고치고, 남긴 예외는 `## Output`에 한 줄씩 적습니다.
3. 검토: `review`로 생성되는 `review-standards` 노드는 이 스킬을 항상 불러옵니다. diff가 증명하는 하드 패턴은 `## Rule breaches`에 `anti-slop: <패턴> - <file:line> - <증명>; <고칠 방법>`으로 적히고 `Standards verdict: FAIL`이 됩니다. `auto_recovery`가 켜져 있으면 [리뷰 수정 라운드](#자동-복구)가 지적된 생산 노드를 실행당 한 번 다시 실행합니다.

등급은 두 가지입니다. 하드는 지우거나 단순하게 바꿔도 동작이 그대로라는 것, 또는 버린 타입 정보를 diff로 증명할 수 있는 패턴입니다. 판단은 가독성(Clean Code) 항목과, 증명보다 읽기가 필요한 세 패턴(코드를 되풀이하는 주석, 일어날 수 없는 상태를 막는 가드, 아직 아무도 필요로 하지 않는 추상화)입니다. 판단 항목도 작성 노드는 고쳐야 하지만, 검토에서는 `## Judgment calls`에만 남고 판정을 FAIL로 만들지 않습니다. 주석 한 줄 때문에 수정 라운드(검토 노드 하나에 150-230초)가 돌지 않게 하려는 것입니다.

변경이 추가하거나 고친 줄만 봅니다. 저장소 규칙 문서(CLAUDE.md, AGENTS.md, CONTRIBUTING 등)가 허용한 패턴과 포매터·린터·컴파일러가 이미 잡는 것은 제외합니다. 포매팅, 함수 길이·인자 수 같은 고정 숫자 제한(AI가 한 번만 쓰는 도우미 함수로 잘게 쪼개게 만듦), "주석은 실패"라는 규칙(이 레포는 이유를 적는 주석을 요구함)은 일부러 넣지 않았습니다.

| 구분 | 패턴 | 스캔 id |
| --- | --- | --- |
| 하드: 군더더기 | 디버그 문(`debugger`, `breakpoint()`, `dbg!`, `printStackTrace()`), 주석 처리된 코드, 요청된 동작 대신 남긴 `TODO` | `debug-leftover`, `commented-out-code`, `todo-stub` |
| | 삼키거나 다시 던지기만 하는 catch·except·`if err != nil {}` | `swallowed-error`, `rethrow-only-catch` |
| | `c ? true : false`, `if (c) return true; return false`, `result` 같은 이름으로 받아 바로 반환 | `boolean-ceremony`, `pass-through-variable` |
| 하드: 버린 근거 | 계약의 최상위 타입(`unknown`·`any`, `Any`, `interface{}`, `Object`. 외부 데이터를 파싱하는 함수의 입력은 예외), 열린 딕셔너리(`Record<string, unknown>`, `dict[str, Any]`, `Map<String, Object>`) | `top-type`(TS는 `any`·`object`만), `open-dictionary` |
| | 연쇄 단언, `SAFETY:` 이유 없는 캐스트(`as T`, `cast()`, `x.(T)`, `(User) obj`, `unsafe`), 이유 없는 억제(`@ts-ignore`, `# type: ignore`, `@SuppressWarnings`) | `chained-assertion`, `unreasoned-assertion`, `suppression-without-reason` |
| | 이름 문자열로 하는 리플렉션(`Reflect.get`, `getattr(o, "x")`) | `reflection` |
| | 아는 값을 넓은 타입으로 넓히기, 넓혔다가 다시 단언, 경계 파서 밖의 `typeof`·`isinstance` | 스캔 없음 |
| 하드: 테스트 | 모듈 패치(`vi.mock`, `jest.mock`, `Mockito.mockStatic`, `mock.patch`) | `module-mock`(JS·TS·Java) |
| 하드: JS·TS | 연달은 `filter`·`map`, `reduce`에서 누적값 복사, 조건부 빈 객체 스프레드 | `two-pass-filter-map`, `growing-copy`, `conditional-empty-spread` |
| 판단 | 되풀이 주석, 불가능한 상태 가드, 필요 없는 추상화, 깊은 중첩, 플래그 인자, 이름 없는 매직 값, 상태를 바꾸는 조회 함수, 이중 부정, 형태를 말하는 이름(`UserShape`, `strName`), 여러 일을 하는 함수 | 스캔 없음 |

스캐너는 `hooks/engine/slop-scan.ts`에 있고, 모든 패턴마다 잡아야 할 예와 잡으면 안 되는 비슷한 예를 `tests/slop-scan.test.ts`에 둡니다. 잘못 걸린 경우는 편집마다 모델의 주의를 빼앗으므로, 규칙은 놓치는 쪽을 감수하고 정확도를 우선합니다. 2026-10-12에 이 저장소의 TS 10,573줄에 돌려 TS 파라미터의 `unknown`(36건 중 30건이 파서 입력)과 루프를 닫는 `}`를 if로 읽은 경우를 걸러냈습니다. 남은 186건은 모두 규칙이 겨냥한 모양이었고, 동작을 바꾸지 않고 정리할 수 있는 것(빈 catch 2, 이중 단언 1, 검사형으로 바꿀 수 있는 단언 28)은 정리했으며, 나머지는 이 저장소의 관용구로 [개발](development.md#개발)에 예외로 적었습니다. 확장자로 언어를 고르며, Kotlin·C#·Swift·Scala·Dart·C·C++·PHP는 중괄호 언어 공통 규칙만 받습니다.

#### 보안 검토 (선택)

`review.security`에 시큐어코딩 가이드를 고르면 보안 검토가 멀티에이전트로 붙습니다. 고르지 않으면 보안 노드는 하나도 없고, 기존 정의는 해시와 지문이 이전과 같아서 `amend`해도 다시 실행되는 노드가 없습니다.

| id      | 가이드                                                      | 기준 파일                                     |
| ------- | ----------------------------------------------------------- | --------------------------------------------- |
| `kisa`  | KISA·행정안전부 소프트웨어 개발보안 가이드, 구현 단계 보안약점 49개(2021 개정판) | `skills/secure-coding/references/kisa.md`  |
| `owasp` | OWASP Top 10:2025와 CWE Top 25(2025)                         | `skills/secure-coding/references/owasp.md` |
| `agent` | 에이전트 프롬프트·도구 권한·학습 스킬·완료 근거의 신뢰 경계(프로젝트 기준, 2026-10-13) | `skills/secure-coding/references/agent.md` |

```yaml
review:
  request: 로그인 API를 추가한다.
  security: [kisa]        # [owasp], [agent], [kisa, owasp, agent]도 가능. 빼면 보안 검토 없음
```

검토는 세 단계이고, 각 에이전트는 자기 몫 하나만 맡습니다.

`agent`는 기존 관점·후보별 반박 검증·집계 흐름을 그대로 씁니다. 외부 CLI를 설치하지 않습니다. 의존 노드 출력의 지시문 승격, 모델 출력의 명령·경로 유입, 권한 우회, 학습 근거와 프로젝트 범위, 비밀 유출·미검증 완료, 작업량 제한을 확인합니다. 숨은 문자나 수상한 문구만으로 위반을 확정하지 않고 실제 경로의 통제 누락을 증명해야 합니다. 선택하지 않은 실행에 보안 노드를 자동 추가하지 않습니다. 의존 노드 출력과 학습 입력에는 출처가 있는 데이터이며 권한을 부여하지 않는다는 지침을 전달하지만, 이 지침만으로 프롬프트 주입 방어를 보증하지는 않습니다.

```
사용자 노드 ─┬─ security-injection ─┐        (실행 중 추가)
             ├─ security-resources ─┤   후보마다 security-verify-<관점>-<n>
             ├─ security-access ────┤          │
             ├─ security-crypto ────┼──────────┴──── review-security ── commit
             ├─ security-errors ────┤
             ├─ security-memory ────┤
             └─ security-integrity ─┘
```

1. 관점 노드 7개(`injection`, `resources`, `access`, `crypto`, `errors`, `memory`, `integrity`)가 사용자 노드 뒤에 병렬로 돕니다. 기준 파일의 각 행에는 관점 열이 있고, 관점 노드는 고른 가이드에서 자기 관점 행만 적용해 후보 위반을 찾습니다. 확신이 없으면 후보로 올리고(재현율 우선), 결과는 노트의 `## Candidates`에 JSON 배열로 씁니다. 관점당 최대 8건이고, 같은 패턴의 반복은 한 후보로 합칩니다.
2. 관점 노드가 끝나면 플러그인이 그 JSON을 읽어 후보마다 검증 노드 `security-verify-<관점>-<n>`을 실행 중에 추가합니다. 검증 노드는 어떤 노드에도 의존하지 않아 관점 노드의 출력도 구현 노드의 보고도 받지 않고, 자기 후보 하나만 봅니다. 그 후보를 반박하려고 시도하면서 (1) 변경이 그 줄을 추가하거나 고쳤는지, (2) 인용한 가이드 행이 해당하는지, (3) 변경 밖 호출부·미들웨어·프레임워크 기본값까지 따라가도 통제가 없는지를 증거와 함께 확인하고, 셋 다 맞을 때만 `Candidate verdict: CONFIRMED`, 아니면 `REFUTED`를 씁니다.
3. `review-security`는 관점 노드 전부와 추가된 검증 노드 전부를 기다린 뒤, 새로 판단하지 않고 결과만 모아 보고서를 씁니다. 판정은 기계적으로 막습니다. 검증 노트 폴더(`<notes>/security-verify/`)에 `Candidate verdict: CONFIRMED`가 하나라도 있으면 `review-security`의 검사가 실패하므로, 보고서가 PASS라고 써도 커밋되지 않습니다. `commit`이 있으면 세 검토(spec, standards, security)가 모두 PASS일 때만 커밋합니다.

- 위반 기준: 변경이 추가하거나 고친 줄에 고른 가이드의 행이 해당하고 그 행이 요구하는 통제가 없을 때만 위반입니다. 변경하지 않은 코드, 고르지 않은 가이드에만 있는 위험, 반박된 후보는 판단 사항으로 적고 통과합니다. 저장소에 설정된 린터나 보안 스캐너가 잡는 것은 적지 않습니다.
- 실패 처리: 관점 노드의 JSON이 깨졌거나, 8건을 넘거나, 고르지 않은 가이드를 인용하거나, 프로젝트 밖 경로를 가리키면 그 관점 노드가 이유와 함께 실패합니다. 이때 검증 노드는 만들지 않고 `review-security`와 커밋은 건너뜁니다.
- 이전 결과 정리: 생성된 노드는 시도 전에 자기 노트를 지우고, 관점 노드는 자기 검증 폴더(`security-verify/<관점>/`)를 통째로 지웁니다. 같은 key로 돌린 이전 실행이 남긴 CONFIRMED 파일로 실패하지 않게 하기 위해서입니다.
- 비용: 검증 노드는 어떤 노드에도 의존하지 않아서 관점 노드의 추론도, 구현 노드의 자기 보고도 받지 않습니다. 그래서 그래프에서는 시작 노드처럼 보입니다. 검토 한 번에 에이전트 8개(관점 7 + 집계 1)와 후보 수만큼의 검증 에이전트가 듭니다. 드라이런 미리보기와 승인 화면에는 관점 노드까지만 보이고, 검증 노드는 실행 중에 나타납니다. 동시 실행 한도(`max_concurrent`, 기본 8)를 넘는 노드는 차례를 기다립니다.
- `amend`: 선언된 정의에는 실행 중 추가된 검증 노드가 없으므로, `amend`하면 검증 노드를 만든 관점 노드가 다시 실행되어 검증 노드를 새로 만듭니다. 검증 노드가 실행 중이면 `amend`는 거부됩니다.
- 고르는 방법: 계획 스킬은 요청이 시큐어코딩, 보안 검토, KISA, OWASP를 언급하거나 프로젝트 규칙 파일이 가이드를 지정할 때만 `security`를 넣고, 기본으로는 넣지 않습니다. 실행마다 고르려면 요청에 "KISA 기준으로 보안 검토까지"처럼 적거나 정의 파일에 `security`를 씁니다. 프로젝트 전체에 적용하려면 그 프로젝트의 `CLAUDE.md`나 `AGENTS.md`에 "코드 변경 실행은 `review.security: [kisa]`로 검토한다" 같은 한 줄을 둡니다.
- 구현 노드: 코드를 쓰는 노드도 `load_skills: ["dag-workflow:secure-coding"]`과 프롬프트의 가이드 id로 같은 기준을 따르게 할 수 있습니다. 가이드 id가 없으면 그 노드는 `missing-input`으로 실패합니다.

규칙은 두 곳에서 실행됩니다.

1. 편집 시점: Edit이나 Write가 코드 파일(`.py`, `.js`, `.ts`, `.java` 등)에 닿으면 플러그인이 새 내용을 임시 폴더의 같은 상대 경로에 복사해 검사합니다. 그 호출이 추가하는 줄에 `block` 규칙(현재는 하드코드된 중요정보 2-6)이 걸리면 파일에 쓰기 전에 호출을 거부합니다. 거부 사유에는 걸린 줄의 내용을 다시 적지 않습니다. 비밀값이 거부 사유를 통해 대화 기록에 남지 않게 하기 위해서입니다. 나머지 히트는 호출이 끝난 뒤 anti-slop 스캔처럼 모델이 읽는 컨텍스트로 붙습니다. 메인 대화와 DAG 노드 모두에 적용됩니다.
2. 보안 검토: `review.security`가 `kisa`나 `owasp`를 고른 실행에서 관점 노드가 끝나면, 플러그인이 실행의 변경(추적 파일은 `git diff HEAD`의 추가 줄, 새 파일은 전체)을 한 번 검사합니다. 그 관점에 속하는 히트를 관점 노드의 후보 옆에 더하고, 후보마다 검증 노드가 붙습니다. 같은 규칙의 여러 히트는 후보 하나로 합치고, 관점 노드가 이미 보고한 줄은 다시 더하지 않습니다. 더한 후보는 관점 노트의 `## Semgrep candidates`에 기록되어 `review-security`가 검증 노드 수와 맞춰 봅니다. 히트는 위반 판정이 아니라 후보입니다. 도구 오탐(예: `long` 타입 경로 변수, ETag용 MD5)은 검증 노드가 반박합니다.

- 설치: semgrep이 PATH에 있어야 합니다(`brew install semgrep` 또는 `pipx install semgrep`). 세션마다 첫 검사 때 `semgrep --version`을 한 번 확인하고, 없으면 두 곳 모두 아무것도 하지 않습니다. `secure_scan: false`로 끕니다.
- 우회 방지: `--disable-nosem`으로 실행하므로 `nosemgrep` 주석으로 규칙을 끌 수 없습니다. 예외는 검증 노드의 REFUTED 판정뿐입니다.
- 한계: Semgrep CE의 taint 규칙은 한 함수 안의 흐름만 추적합니다. 함수나 파일을 넘는 흐름은 관점 노드 프롬프트가 맡도록 안내합니다. 편집 시점 검사는 호출마다 semgrep을 한 번 실행하므로 코드 파일 편집이 1초 안팎 늦어집니다.
- 규칙 추가: 규칙 파일에 규칙을 더하고 `tests/semgrep/kisa-<언어>.*`에 `ruleid:`(잡아야 할 줄)와 `ok:`(잡으면 안 되는 줄) 예제를 더한 뒤 `semgrep --test --metrics off --config skills/secure-coding/rules tests/semgrep`로 확인합니다. 런타임 코드는 고치지 않습니다.
- 모델 등급: 보안 노드는 모두 `review.category`(기본 `standard`)를 씁니다. 더 깊게 보려면 `category: hard`로 올립니다.
- 가이드 추가: `hooks/engine/stages.ts`의 `SECURITY_GUIDES`에 id와 이름을 한 줄 넣고, `skills/secure-coding/references/<id>.md`에 항목, 판본, 행마다 관점 열(`SECURITY_LENSES`의 id 중 하나)을 쓰고, `skills/secure-coding/SKILL.md`의 가이드 표와 이 표에 한 줄씩 더합니다. 도구 스키마의 허용 값은 `SECURITY_GUIDES`에서 만들어집니다.

## 자동 복구

복구 요청에는 실패한 명령 검증에서 확인한 오류 근거를 `observedFailures`로 함께 전달합니다. 누락 프로그램, 프로젝트 모듈 경로, 외부 패키지, 연결 거부, 포트 충돌, 권한 오류를 구분하되 최종 복구 분류는 아닙니다. 패키지 설치나 서비스 실행이 원래 작업에 포함될 수 있으므로, 환경 오류라는 이유만으로 복구를 중단하지 않습니다. 성공한 검사, 종료 코드 0에서의 기대 불충족, 종료 상태를 모르는 결과는 이런 분류 근거로 사용하지 않습니다. 기존 `check-defect`의 재시도 제외 규칙은 유지합니다.

`auto_recovery`(기본 `true`)가 켜져 있고 Jev를 쓸 수 있으면, 실패한 노드의 원인을 Jev가 분류하고 확신도가 `jev_confidence` 이상일 때만 다시 실행합니다.

- `transient`(일시 오류): 같은 등급 모델로 다시 실행합니다.
- `implementation`(구현 실수): Opus로 다시 실행합니다.
- `missing-input`, `clarification`, `permanent`, 낮은 확신도, API 실패, 사용자 취소, 인계 중인 실행, 검증 계약이 없는 노드는 자동으로 재시도하지 않습니다.
- 리뷰·감사 노드의 FAIL 판정(`Spec`/`Standards`/`Security verdict: FAIL`, `partial/supporting-output`)도 재시도하지 않습니다. 같은 결과물을 다시 리뷰해도 판정은 그대로이기 때문입니다(2026-10-12, 실제 run 4개에서 Opus 재시도 7번이 같은 FAIL을 되풀이하며 54분을 썼습니다). 대신 실행에서 실패한 노드가 이런 판정뿐이면, 실행당 한 번 **리뷰 수정 라운드**를 돕니다. 지적이 가리키는 producer(생산 노드가 하나면 그 노드, 여럿이면 지적에 나온 `파일:줄`이 `writes` 범위에 드는 노드)를 지적 내용을 프롬프트에 붙여 다시 실행하고, 그 뒤의 노드(리뷰·커밋)도 다시 실행합니다. 생성된 리뷰 노드의 지적은 노트의 `## Findings`·`## Rule breaches`·`## Breaches` 절에서 읽습니다. 지적은 모두 합쳐 4,000자 안에서 producer 프롬프트에 붙이는데, 리뷰어마다 고르게 나눕니다. 짧은 지적은 그대로 싣고, 쓰고 남은 몫은 긴 지적을 낸 리뷰어들이 나눠 씁니다. 예전에는 리뷰어 순서대로 예산을 썼기 때문에, 2026-10-19 리허설에서 세 리뷰어가 모두 FAIL하자 `review-spec`과 `review-standards`가 예산을 다 쓰고 `review-security`의 지적은 빈 블록으로 전달되어 라운드가 보안 위반을 고치지 못했습니다. 리뷰가 통과하면 정착 메시지에 "자동 수정 라운드가 producer를 다시 실행했다"는 줄이 붙고, 다시 FAIL이면 "라운드를 이미 썼다"는 줄과 남은 지적을 담아 정착 메시지를 보내고, 지적이 어느 `writes`에도 닿지 않으면 예전처럼 바로 정착합니다. 라운드가 다시 실행할 노드 중 이미 끝난 노드가 프로젝트 밖을 바꾸는 노드면 라운드를 돌지 않습니다. `external: true`로 표시했거나, `writes`를 선언하지 않았거나, id·라벨·요약에 push·deploy·publish·upload·migrate·delete·commit·prod 같은 단어가 있는 노드가 여기에 해당합니다. 실제 run에서 외부 작업을 한 노드(`apply-env`, `setup-assets`, `delete-token-row`, `commit-push`)는 모두 `writes`가 없었습니다. `review`가 만든 검토 노드(`review-spec`, `review-standards`, 보안 관점 노드, 검증 노드, `review-security`)는 노트만 쓰므로 `writes`가 없어도 이 검사에서 빼고 다시 실행합니다. 2026-10-19 리허설에서 보안 관점 노드의 빈 `writes` 때문에 `review.security`를 쓴 실행이 라운드를 받지 못한 것을 고쳤습니다. 이때 FAIL은 바로 정착하고, 정착 메시지에 이유와 함께 "지적을 검토하고 외부 작업을 다시 하기 전에 사용자에게 수정 방향을 물으라"는 안내가 붙습니다. 지적이 어느 producer에도 닿지 않아 라운드를 돌지 않을 때도 이유가 붙습니다. `auto_recovery=false`면 이 라운드도 돌지 않습니다.

  **지적 장부(finding ledger).** 라운드는 이제 실패한 리뷰어마다 생산 노드에 보낸 지적 원문을 체크포인트의 라운드 기록에 남기고, 고치기 전의 생산 노드 `writes` 파일(디스크에 있는 것만, 최대 200개)을 `.claude/dag/runs/<run_id>/review-fix-<n>/before/`에 복사합니다. 복사에 실패해도 라운드는 그대로 돌고, 다시 도는 리뷰어는 변경을 기록하지 못했다는 안내를 읽습니다. 다시 실행되는 `review-spec`과 `review-standards`는 프롬프트 끝에 리뷰어별 지적 블록과 수정이 만든 diff(12,000자까지, 넘으면 전체 길이를 밝히고 자름)를 받고, 규칙 네 가지를 따릅니다. (1) 자기 지적은 `## Ledger`에 RESOLVED(수정이 없앰), OPEN(아직 있음), WITHDRAWN(애초에 요청이나 규칙 위반이 아니었다고 다시 판단함) 중 하나로 `file:line` 근거와 함께 적고, WITHDRAWN이면 그 지적이 틀렸다는 근거도 적습니다. (2) 어떤 지적이든 그것을 풀려고 한 변경은 요청받은 작업으로 보며, 요청 문장과 충돌하면 `## Deferred`에 적습니다. (3) 새 지적은 수정이 바꾼 줄에 있을 때만 FAIL 사유가 되고, 나머지는 `## Deferred`에 적습니다. (4) 자기 지적이 OPEN이거나 그런 새 지적이 있을 때만 FAIL하며, OPEN 지적은 아무리 사소해도 FAIL 사유입니다. WITHDRAWN은 아래 측정에서 OPEN으로 표시하고도 통과한 사례 때문에 더했습니다. 생산 노드의 마무리 지시도 바뀝니다. `writes`에 든 파일을 가리키는 지적은 원래 작업이 요구하지 않은 것을 요구하더라도 자기 일이고, 리뷰어는 작업이 아니라 요청에 비춰 결과를 판단하므로 범위 안에서 풀되 원래 작업이 요구한 것은 모두 유지하고 지적이 짚지 않은 것은 바꾸지 말며, 범위 안에서 풀 수 없는 지적은 `failed`로 끝내며 그 지적을 밝히라는 내용입니다. 보안 관점 노드, 검증 노드, `review-security`의 프롬프트는 그대로입니다. 배경은 `examples/secure-coding`을 헤드리스로 다섯 번 실행한 측정입니다(2026-10-19~20, 1막 없이 실행해 검색 엔드포인트가 없는 상태). 수정 라운드 뒤에 `review-spec`이 다시 FAIL한 것이 5번 중 5번이었고, 보안 수정이 넣은 접근 검사를 어떤 시도는 요청하지 않은 변경이라 보고하고 어떤 시도는 받아들였으며, 메인 대화는 매번 amend를 한두 번 하거나 새 run을 시작해야 했습니다. 이 효과는 2026-10-20에 `review_ledger`를 끈 실행과 켠 실행을 짝지어 쟀습니다. `examples/secure-coding`의 3막(`/dag run demo/review.yaml`, sonnet)을 1막 상태(SQL 인젝션이 있는 검색 엔드포인트가 커밋되지 않은 채 남은 상태)에서, 끈 실행과 켠 실행을 동시에 시작한 쌍으로 세 쌍 돌렸고 실행마다 키를 따로 두어 리뷰 노트 폴더가 겹치지 않게 했습니다. 끈 쪽은 첫 settle이 3번 중 3번 실패했고(`review-spec`이 라운드 뒤에 매번 다시 FAIL하며, 보안 수정이 넣은 소유자·관리자 403을 어떤 요청 문장도 다루지 않는 동작이라고 보고했습니다), 메인 대화가 두 번은 amend 한 번으로 커밋까지 갔고 한 번은 실패로 끝나 커밋을 건너뛰었습니다. 비용은 평균 4.05 USD, 벽시계는 평균 276초, 노드 attempt는 35/51/50이었습니다. 켠 쪽은 첫 settle이 3번 중 3번 자동 라운드만으로 완료되었고 메인 대화의 조치가 없었으며, `review-spec`은 3번 모두 FAIL에서 PASS로 바뀌었고 다시 돈 리뷰어는 403을 "ledger fix, requested work"라고 불렀습니다. 비용은 평균 2.86 USD, 벽시계는 평균 191초, attempt는 34/33/36이었습니다. 커밋된 변경 다섯 건(켠 3, 끈 2)은 모두 검색 파라미터를 `LIKE ?`로 바인딩하고 삭제 전에 소유자 또는 관리자를 확인합니다. 켠 실행의 리뷰 노트에서는 두 가지가 보였습니다. 두 실행에서 `review-spec`이 앞서 적은 MD5 ETag 노트를 OPEN으로 표시하고도 통과했고(규칙 4는 OPEN 지적이 있으면 FAIL이라 하며, 보안 검증 노드가 모두 MD5 후보를 반박했으니 통과 자체는 옳았지만 규칙이 느슨하게 적용되었습니다), 세 실행 모두에서 다시 돈 `review-spec`이 403-먼저-404 충돌을 규칙 2대로 `## Deferred`에 적어 사람의 결정으로 넘겼습니다. WITHDRAWN 규칙을 넣고 `review_ledger`를 켠 실행을 1막 상태에서 여섯 번 다시 돌렸더니 모두 메인 대화 조치 없이 자동 라운드만으로 완료되었고(평균 2.90 USD, 202.5초), OPEN 지적이 있는데 통과한 실행은 없었으며, `review-spec`이 403-먼저-404 충돌을 여섯 번 모두 `## Deferred`에 적었습니다. 자세한 표는 `examples/secure-coding/README.md`에 있습니다. 한계: 세 쌍은 유의성을 말하기에 적고, 쌍이 동시에 돌았으며, 비용에 settle 뒤 메인 대화의 턴이 들어 있어 끈 쪽의 추가 비용 일부는 amend 턴입니다. 자세한 표는 `examples/secure-coding/README.md`에 있습니다. `review_ledger: false`면 리뷰어와 생산 노드의 프롬프트·노트는 장부 이전과 같고 복사도 하지 않습니다.
- 검사 자체의 결함(`check-defect`)도 재시도하지 않고 Jev에 묻지도 않습니다. 검사 프로그램이 PATH에 없어 시작되지 못했거나, 검사의 셸이 종료 코드 127로 "command not found"를 냈거나(`./dist/cli`처럼 경로로 부른 프로그램은 제외), 워커가 `DAG_NODE_STATUS: failed: check-defect - <이유>`로 보고한 경우입니다. 다시 실행해도 같은 검사가 또 실패하기 때문입니다. 오류는 `check-defect:`로 시작하고, 메인 대화가 검사를 `amend`로 고칩니다.
- 노드마다 자동 추가 시도는 최대 2번입니다. 원래 프롬프트·범위·목표를 그대로 두고 실패 이유와 "선언한 검증을 다시 실행하라"는 지시만 덧붙이며, 사용한 횟수는 체크포인트에 남아 다시 늘어나지 않습니다.
- 실패 때문에 건너뛴 하위 노드도 함께 대기 상태로 돌아갑니다. 모든 복구 판단은 [판단 기록](#판단-기록)에 남습니다.

## 동일 실패 반복 안내

기존 일반 `tool.call` 결과 처리에서 단순한 전경 Bash 검증 명령(`bun test`, `npm`/`pnpm`/`yarn`의 `test`·`run test`, `claude plugin test`, `tsc --noEmit`)을 관측합니다. 같은 실행 주체가 같은 명령으로 같은 명시적 비정상 종료 결과를 다시 받으면 `[dag-workflow:repeat-check]` 안내를 한 번 붙입니다. 기존 도구 결과·오류·컨텍스트는 유지하고, 선언된 완료 검증은 계속 실행합니다. 셸 조합·리다이렉션·변수 치환·watch·스냅샷 갱신 명령은 대상이 아닙니다.

관측된 수정이나 환경 변경 가능성이 있는 도구 호출, 겹치는 호출, 성공·중단·잘린 결과는 비교를 무효화합니다. 백그라운드 실행이 감지되면 그 완료를 다른 결과에서 추정하지 않고 `/clear`나 새 세션까지 반복 안내를 중단합니다. 이 때문에 실행 중인 작업을 멈추려고 `/clear`할 필요는 없습니다. 기록은 주체별 마지막 실패 하나, 최대 64개를 메모리에만 보관하며 작업자 응답 종료·세션 종료·clear 때 정리합니다. 새 훅·타이머·모델 호출·파일 순회는 추가하지 않으며, 파일이나 외부 서비스가 실제로 그대로임을 증명하는 검증 캐시는 아닙니다.

반복 실패 비교에서는 ANSI 색상, 인식한 테스트 러너의 실행 시간 표기, 로그 수준(INFO·WARN·ERROR·DEBUG·TRACE)이 뒤따르는 ISO timestamp 접두사만 정규화합니다. 기대값·실제값·오류 코드·파일과 줄·테스트 수·시간 자체를 검증하는 값은 유지합니다. 도구에 보이는 원문 결과는 바꾸지 않습니다.

## 컨텍스트 보존

세션마다 `.claude/dag/context/<session>.json`에 원본 사용자 요청 마지막 8개(각 20,000자까지, 넘으면 잘렸다는 표시를 붙임)와 고정 노트를 저장합니다. 이 원본에서 매번 8,000자 이하의 복원 블록(JSON)을 새로 만들고, 여기에는 현재 목표, 노트, 이 세션의 실행·노드 상태, 검증 결과, 복구 횟수, 체크포인트와 보고서 경로 같은 출처 참조가 들어갑니다. 요약을 다시 요약하지는 않으며, 원본과 체크포인트가 기준입니다. 이 파일은 세션이 실행을 소유하거나, 고정 노트가 있거나, 이미 파일이 있을 때만 씁니다. DAG를 쓰지 않는 평범한 대화의 요청은 메모리에만 두고(복원 블록은 그대로 동작), 세션의 첫 실행이 시작될 때 그때까지의 요청을 함께 저장합니다.

복원 블록은 대화의 첫 컨텍스트 블록으로 모델에 전달되고, 압축(compaction) 뒤와 `/clear` 뒤에도 다시 넣습니다. 이후 프롬프트에서는 모델이 마지막으로 본 뒤 이 세션의 실행이나 노트 상태가 바뀐 경우(예: 패널에서 실행을 취소했거나 노트를 고정한 경우)에만 사용자 프롬프트에 붙습니다. 플러그인이 보내는 진행·정산(settle)·keep-alive 메시지에는 붙지 않고, 짧은 프로토콜 안내문은 모든 프롬프트에 붙습니다. `/clear` 뒤에는 이전 컨텍스트를 새 세션으로 옮기고, 재개한 세션은 자기 기록을 다시 읽습니다. `/dag context`로 내용을 보고, `/dag note`로 노트를 고정하거나 지웁니다.

노드가 실행 중일 때 `/clear`를 하면 실행 소유권과 노트는 새 세션으로 옮겨지고 작업자도 계속 실행됩니다. 다만 Claude Code가 그 순간 작업자가 실행 중이던 셸 명령을 종료할 수 있습니다(실측: exit 137). 작업자는 보통 명령을 다시 실행하지만, 허용 규칙에 없는 형태로 다시 실행하면 권한 확인을 기다리며 멈출 수 있습니다. 노드가 오래 걸리는 셸 명령을 실행 중이면 `/clear` 대신 `/compact`를 쓰세요. 실측에서 압축은 실행 중인 셸을 끊지 않았습니다.

## 판단 기록

라우팅·도구 승인·복구·실행 방식·표시 방식 판단을 세션마다 마지막 200개까지 `.claude/dag/decisions/<session>.json`에 남깁니다. 기본값 `auto`에서는 Jev에 물은 사용자 프롬프트마다 실행 방식 기록(대화형 세션의 패널 화면에서는 표시 방식 기록도)이 남으므로, DAG를 쓰지 않는 프로젝트에서도 첫 프롬프트에 `.claude/dag/.gitignore`와 이 파일이 생깁니다. 기록에는 제안값, 선택값, 판단 주체(`jev`/`baseline`/`rule`), 확신도, 선택지별 확률, 규칙 버전, 기준 확신도, 지연 시간, 결과(`applied`, `low-confidence`, `timeout` 등), 입력 상태의 해시가 들어갑니다. 결과는 Jev의 답이 어떻게 처리됐는지, 판단 주체는 최종 값을 누가 정했는지를 뜻합니다. 그래서 최종 감사 규칙이 Jev의 `trivial`을 덮어쓰면 결과는 `applied`, 판단 주체는 `rule`로 남습니다. API 키와 도구 입력 전체는 저장하지 않습니다. `/dag decisions [id]`, 도구 액션 `decisions`, 패널의 Decisions 탭으로 봅니다. 노드 작업자의 도구 승인 기록에는 `runId`와 `nodeId`도 들어가고, 비대화형 세션에서 호출이 `ask`로 남았으면 그 원인을 적은 `note`도 붙습니다([결과 전달](#결과-전달)의 **비대화형 세션의 도구 허용** 문단).

## 실행 기록 (trajectory)

같은 정의를 여러 번 실행하면 리뷰어의 판정, 리뷰 수정 라운드 여부, 커밋 여부가 실행마다 다를 수 있습니다. 체크포인트는 노드마다 마지막 시도만 남기고, 보고서 `runs/<run_id>/<node>.md`는 다음 시도가 덮어쓰며, 리뷰어 노트는 리뷰어가 다시 시작하기 전에 지웁니다. 그래서 체크포인트만으로는 두 실행이 어디서 갈렸는지 알 수 없습니다. `trajectory_log: true`로 켜면 그 과정을 이벤트로 남깁니다. 기본값은 꺼짐입니다.

- **위치:** 실행의 이벤트는 `.claude/dag/trajectories/<run_id>/`에, 메인 대화의 턴은 `.claude/dag/trajectories/session-<session_id>/`에 이벤트 하나당 파일 하나(JSON 한 줄)로 씁니다. 파일 이름은 `<시각 ms>-<순번>-<종류>[-<노드>].jsonl`이라 이름순이 발생 순서입니다. 실행이 끝날(settle) 때마다 그 실행의 이벤트를 이름순으로 이어 붙인 `.claude/dag/trajectories/<run_id>.jsonl`을 다시 씁니다. 세션 폴더는 이어 붙이지 않으니 `cat .claude/dag/trajectories/session-<id>/*.jsonl`로 읽습니다.
- **쓰기:** 기록은 별도 쓰기 큐로 보내고 실행은 기다리지 않습니다. 쓰기에 실패하면 디버그 로그에 남기고 실행은 계속합니다. 노드 종료 기록은 완료를 반영하기 전에 노트와 diff를 먼저 읽습니다. 반영 뒤에 시작되는 다음 시도가 노트를 지우기 때문입니다.
- **가림과 자르기:** 모든 문자열에서 Jev 요청을 보낼 때와 같은 비밀값 패턴(개인 키, Bearer 토큰, AWS·GitHub·Slack 토큰, `sk-` API 키, `password=` 같은 할당)을 `[REDACTED:<종류>]`로 바꿉니다. 프롬프트·답·노트·diff는 64,000자, 도구 입력의 문자열과 도구 결과는 4,000자에서 자르고 원래 길이를 적습니다. 이벤트 한 줄이 1,000,000자를 넘으면 더 짧게 자르고, 그래도 넘으면 이벤트 이름과 길이만 남깁니다. 패턴에 없는 형태의 비밀값은 가리지 못하니 기록을 공유하기 전에 확인하세요.
- **보관:** `retention_days`로 지우지 않습니다. 필요 없어진 기록은 직접 지웁니다. `.claude/dag/.gitignore`가 `*`이므로 커밋되지 않습니다.

| `run.retry`, `run.amend` | retry·amend 반영 | `nodeIds`·`prompt` 또는 `rerun`·새 `definition` |
| `node.start` | 노드 에이전트 시작 | `attempt`, `agentId`, `model`, `subagentType`, `category`, `recovery`, 에이전트가 받은 `prompt` 원문(상위 노드 결과, 리뷰 수정 지적, 복구 맥락 포함). 시작 실패면 `error` |
| `node.end` | 노드 에이전트 종료 | `state`, `error`, `answer`(보고서 원문), `verification`(검사별 결과), `expansion`(보안 관점이 만든 검증 노드 id), `notes`(검사가 읽는 프로젝트 밖 노트 파일의 그 시점 내용: 리뷰어·보안 관점·후보 검증 노트), `diff`(`writes`를 선언한 노드의 HEAD 대비 변경과 새 파일 내용), `usage`(토큰 수와 모델) |
| `node.transcript` | `node.end` 직후 | 에이전트 대화의 행: 말한 텍스트, 도구 호출마다 `tool`·`input`·모델이 읽은 `result`·`isError` |
| `rework` | 리뷰 수정 라운드 | `round`, `reviewers`, `producers`, 생산 노드에 붙인 지적 `note` 원문. 라운드를 건너뛰면 `skip`과 이유 |
| `run.settle` | 실행 종료 | `status`, `cancelReason`, `reviewFix`, 노드별 `state`·`attempt`·`model`·`category`·시작/종료 시각·`error`·`recovery`·검증 상태 |
| `main.turn` | 메인 대화 턴 종료 | `turnId`, `reason`, `durationMs`, `usage`, 직전 기록 이후의 메인 대화 행 |

모든 이벤트에는 `at`(ms)과 `sessionId`가 있고, 실행 이벤트에는 `runId`, 노드 이벤트에는 `nodeId`가 있습니다. 예를 들어 실행 여러 개에서 후보 검증 노드의 판정을 모으려면 다음처럼 읽습니다.

```bash
jq -c 'select(.kind == "node.end" and (.nodeId | startswith("security-verify-"))) | {runId, nodeId, attempt, state, verdict: ([.notes[].text | scan("Candidate verdict: [A-Z]+")] | last)}' .claude/dag/trajectories/dag_*.jsonl
```

한계는 다음과 같습니다.

- 노드 에이전트의 대화는 호스트가 서브에이전트용으로 저장한 행이라 도구의 저장 기록(`result` 원본)이 없고, 모델이 읽은 텍스트만 있습니다.
- 메인 대화는 호스트가 돌려주는 최근 4,096행 안에서 직전 기록의 마지막 행 뒤를 남깁니다. 압축(compaction)으로 그 행이 사라지면 그때 남은 행을 모두 다시 기록합니다. 재개한 세션은 재개 전 행을 다시 쓰지 않습니다.
- 노드를 `send`로 조정한 메시지는 별도 이벤트가 아니라 메인 대화 턴의 도구 호출 입력으로 남습니다.

## 세션과 인계

같은 프로젝트의 세션은 10초마다 자기 상태(실행 목록, 실행 중 노드의 `writes`)를 갱신합니다. 60초 안에 갱신한 세션만 활성으로 봅니다. 활성 세션끼리 `writes`가 겹치면(같은 경로이거나 한쪽이 다른 쪽 폴더 안) 충돌로 **보여 주기만** 하고, 실행을 멈추거나 조정하지는 않습니다. 와일드카드가 들어간 범위는 비교하지 않습니다.

실행 소유권은 명시적인 인계로만 옮깁니다.

1. 원래 세션에서 `/dag handoff <run> <session>`: 같은 프로젝트의 활성 세션에만 제안할 수 있습니다. 새 노드는 시작하지 않고(대기 노드는 `paused`), 실행 중인 노드는 끝날 때까지 둡니다. 실행 중인 노드가 모두 끝나 제안이 `offered`가 된 뒤에는 원래 세션을 닫아도 됩니다.
2. 받는 세션에서 `/dag accept <run>`: 실행 중인 노드가 모두 끝난 뒤에만 수락됩니다. 끝나지 않은 노드만 이어서 실행하고, 완료된 노드와 결과는 그대로 둡니다. 원래 세션의 고정 노트와 보드 전체도 가져옵니다(보드의 `sessionId`는 받는 세션 것으로 바뀌고, 원래 세션의 보드 파일은 그대로 둡니다).
3. 취소는 원래 세션에서 `/dag handoff <run> cancel`입니다.

다른 프로젝트 세션은 대상이 될 수 없습니다. 인계 알림이 와도 패널만 새로 고칠 뿐 자동으로 수락하지 않습니다. `attach`는 소유 세션이 아직 활성이거나 인계 중인 실행이면 거부합니다(`owner_active`, `manual_handoff_required`).

## 실행 규칙

- 의존 노드가 모두 `completed`인 노드가 `scheduled`가 되고, 실행 수 상한(기본 8)까지 동시에 시작됩니다.
- 노드가 실패하거나 취소되면 그 하위 노드는 `skipped`가 됩니다. 관계없는 노드는 계속 실행됩니다.
- 노드 상태는 서브에이전트 턴 종료 이유로 정합니다. `aborted`면 `cancelled`, `error`/`refusal`이면 `failed`이고, 답변 마지막 줄이 `DAG_NODE_STATUS: failed: <이유>`여도 `failed`입니다.
- 노드 작업자는 명령을 포그라운드로 실행하고, 자기가 시작한 백그라운드 작업·모니터·백그라운드 서브에이전트가 아직 돌고 있으면 턴을 끝내지 말라고 지시받습니다. 그런데도 백그라운드 작업을 시작한 노드가 `DAG_NODE_STATUS` 줄 없이 턴을 끝내면 플러그인은 바로 검증하지 않고 그 에이전트의 다음 턴을 기다립니다. 30분 안에 다음 턴이 오지 않으면 `ended its turn with background work pending and was not resumed`로 노드를 실패시킵니다.
- 실행이 끝나면 세션에 "완료 주장은 증거로 확인하기 전까지 거짓으로 취급하라"는 지침과 함께 요약 메시지가 들어갑니다.

`start_approval`을 `always`로 하면(기본 `off`) 대화형 세션에서 모델이 `dag` 도구로 시작한 실행은 만들어지기만 하고 노드를 하나도 시작하지 않은 채 보류됩니다. `start` 응답과 스냅샷에 `awaiting_approval: true`와 안내 문구가 붙고, 모델은 사용자에게 한 번 알린 뒤 턴을 끝냅니다. 실행이 보류되면 토스트가 한 번 뜹니다. 프롬프트 아래 상태 줄(`DAG <이름>: 0/3 완료 · 승인 대기 중`)과 프롬프트 위 밴드는 `실행 중 N` 자리에 `승인 대기 중`(영어 `awaiting approval`)을 보여 주고, 도구의 `list` 액션은 그 실행의 `status: running`을 그대로 둔 채 `awaiting_approval: true`를 더해 아직 시작하지 않았음을 알립니다. 보류된 실행 자체는 `/reload-plugins`나 세션 재개 뒤에도 계속 승인을 기다립니다. 보류 표시가 체크포인트에 저장되기 때문입니다. DAG 패널의 승인 블록과 `/dag status`는 사용자가 무엇을 승인하는지 볼 수 있도록 실행 미리보기를 보여 줍니다. 미리보기에는 노드 수와 웨이브 수, 가장 넓은 웨이브와 동시 실행 한도(`max_concurrent`)의 비교, 웨이브별 노드와 카테고리·모델, 쓰기 충돌, 쓰기 범위를 확인하지 못한 노드, lint 경고가 들어갑니다. 승인 블록의 `approve` 버튼(한국어 화면에서는 `승인`)이나 `a` 키, 또는 `/dag approve <run_id>`로 승인하면 실행이 시작되고 모델에 승인되어 시작됐다는 메시지가 갑니다. 같은 블록의 `reject` 버튼(`거절`)이나 `r` 키, 또는 `/dag reject <run_id> [reason]`으로 거부하면 실행이 `Rejected by the user: <reason>`으로 취소되고 모델에 거부되어 아무것도 실행되지 않았다는 메시지가 갑니다. 사용자가 거부한 실행은 모델이 `retry`나 `amend`로 다시 살릴 수 없고, 모델이 같은 키와 같은 정의로 `start`해도 거절하며, 모두 코드 `rejected_by_user`입니다. 사용자는 `/dag retry`로 그 실행을 다시 돌릴 수 있고, 계획을 고치려면 새 키로 시작해야 합니다. `/dag approval`은 인자 없이 쓰면 지금 유효한 설정만 보여 주며 누가 입력해도 됩니다. `/dag approval off|always`로 덮어쓰는 것과 `/dag approve`, `/dag reject`는 사용자 전용이라 모델이 실행할 수 없습니다. 덮어쓴 값은 메모리에만 있어서 다음 `/reload-plugins`까지만 유지되고, 그 뒤에는 `start_approval` 설정으로 돌아갑니다. `start_approval`에 `off`나 `always`가 아닌 값을 쓰면 다른 설정처럼 무시하고 `off`로 둡니다. 예외가 둘 있습니다. 사용자가 직접 입력한 `/dag run`과 비대화형 세션(`claude -p`)은 설정과 관계없이 기다리지 않고 바로 시작합니다. 사용자가 보류된 실행과 같은 정의로 `/dag run`을 입력하면 그 보류된 실행이 승인됩니다.

### `dag` 도구 액션


| 액션                                         | 동작                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `start {definition}`                       | 시작. 같은 키와 같은 정의면 기존 실행 재사용, 다른 정의면 `definition_conflict`. 결과에 계약 점검 `warnings` 포함             |
| `start {path}`                             | `definition` 대신 프로젝트 상대 `.yaml`/`.yml`/`.json` 정의 파일 경로를 받습니다. `/dag run`과 똑같이 읽고 파싱한 뒤 `start {definition}`과 똑같이 시작하므로 계획 스킬 게이트, 린트 `warnings`, 키 재사용이 같습니다. `definition`과 `path` 중 정확히 하나만 허용하며 둘 다 주거나 둘 다 없으면 `invalid_request`입니다. 경로는 `..` 없는 프로젝트 상대 경로이고 `.claude` 밖이며 위 확장자여야 하고, 어기면 `invalid_request`입니다. 읽기나 파싱에 실패하면 경로를 담은 `definition_unreadable`을 돌려줍니다. 모델이 YAML 흐름을 JSON으로 직접 옮겨 적지 않아도 되며, `/dag run`은 계속 사용자 명령이고 절대 경로도 받습니다 |
| `start {dryRun: true}`                     | 정의를 검증만 하고 실행은 만들지 않은 채 `{dry_run: true, preview}`를 돌려줍니다. `definition` 또는 `path`와 함께 씁니다. `preview`에는 단계별 노드 id `waves`, `critical_path`, `node_count`, 노드별 `nodes`(`wave`, 실효 `category`, `model`, `agent`, `depends_on`, `checks`, `writes`, `load_skills`), 동시에 실행될 수 있는 노드끼리 `writes`가 겹치는 쌍 `write_conflicts`, `widest_wave`, `max_concurrent`, `start`가 돌려주는 것과 같은 린트 `warnings`가 들어 있고, 같은 키로 같은 정의가 이미 실행됐다면 `existing_run_id`도 붙고, 아니면 `preview_id`가 붙습니다. `start {preview_id}`는 미리 본 정의를 그대로 시작하므로 모델이 정의를 다시 쓰지 않아도 됩니다(eval에서 이 두 번째 출력에 11-31초가 들었습니다). 시작할 때 키 재사용·검증·PATH 검사를 처음처럼 다시 하며, `preview_id`는 이 세션의 최근 드라이런 8개까지만 기억합니다. 모르는 값은 `unknown_preview`로 거부합니다. `writes`를 선언하지 않은 노드는 `writes`가 null이고, 그런 노드 중 다른 노드와 동시에 실행될 수 있는 것은 `unchecked_writes`에 나열됩니다. 이 노드들은 충돌을 점검하지 못했다는 뜻이며, `writes: []`는 읽기 전용으로 선언한 범위입니다. 알 수 없는 category는 `warnings`에 경고가 추가됩니다. `routing_note`는 category와 모델이 정의가 내놓은 제안값이며 실제로 시작할 때 Jev가 노드를 다시 분류할 수 있다고 알려 주므로, 표시된 category는 최종 감사 규칙까지 적용한 제안값입니다. 계획 스킬 게이트는 드라이런에도 적용됩니다. `dryRun`이 불리언이 아니면 `invalid_request`로 거부하고, `amend`는 `dryRun`을 받지 않고 거부합니다. 사용자는 `/dag preview <file>`로 정의 파일에 같은 미리보기를 볼 수 있습니다. `/dag preview`는 계획 스킬 게이트를 받지 않는 사용자 명령이며, 아무것도 시작하지 않으므로 `/dag run`과 달리 모델 턴 중에도 즉시 실행됩니다 |
| `snapshot {run_id}` / `list`               | 상태 조회(노드 답변 발췌 포함)                                                                            |
| `wait {run_id}`                            | 현재 스냅샷 반환. Claude Code에서는 hook이 10초 넘게 기다릴 수 없어서 블로킹하지 않습니다                                   |
| `cancel {run_id, reason}`                  | 대기 중 노드는 취소, 실행 중 노드 에이전트는 TaskStop으로 중단                                                      |
| `retry {run_id, node_id|node_ids, prompt}` | 실패/취소 노드와 그 때문에 skip된 하위 노드를 다시 실행. 완료 노드는 재사용                                                |
| `amend {run_id, definition}`               | 노드 fingerprint(prompt, category, agent, dependsOn, verify, writes)를 비교해 바뀐 노드와 그 하위 노드만 다시 실행 |
| `send {run_id, node_id, message}`          | 실행 중인 노드에 메시지를 보내 방향을 바꿈                                                                      |
| `attach {run_id}`                          | 소유 세션이 끝난 실행을 이 세션으로 가져와 남은 노드를 이어서 실행. 소유 세션이 활성이거나 인계 중이면 거부                                |
| `context` / `decisions` / `sessions`       | 복원 컨텍스트, 판단 기록, 같은 프로젝트 세션과 충돌 조회                                                             |

## DAG 패널

패널은 위에서 아래로 다음을 보여 줍니다.

- **헤더**: `DAG & Tasks(N)`, 실행 이름과 run id, 실행 상태·완료 수·실패 수. 실행이 둘 이상이면 진행 중인 실행 목록(최대 5개, 눌러서 전환)과 끝난 실행을 펼치는 줄이 붙습니다.
- **관점(뷰)**: 그래프 영역 위의 탭 줄(`▸ Graph   Lanes   Timeline`)이 지금 보이는 뷰를 알려 줍니다. 세 뷰 모두 `Client` 서피스 모듈(`hooks/ui/graph-client.ts`)이 패널의 실제 폭에 맞춰 그립니다. 기본은 자동입니다. 박스가 패널에 무리 없이 들어가면 그래프 뷰, 한 층이 박스 두 줄을 넘거나 박스 줄이 여섯 개를 넘거나 레인이 모자라면 레인 뷰를 씁니다. 탭은 버튼이라 마우스로 눌러 바꿀 수 있고(모델이 작업 중이라 키보드 포커스를 못 얻을 때도 동작), `v`로 자동 → 그래프 → 레인 → 타임라인 순서로 바꾸거나 `/dag view <보기>`로 정할 수도 있습니다. 고른 뷰와 카드 접힘 상태는 프로젝트별로 저장되어 다음 세션에도 유지되고, 다른 프로젝트의 설정에는 영향을 주지 않습니다.
  - **그래프 뷰**: 노드마다 둥근 박스 하나를 층 순서로 그립니다. 박스에는 선택 표시 `>`, 접힘 표시 `[-]`/`[+]`, 라벨, 상태와 실행 중 활동(`… 12s` 응답 대기, `✻` 생각 중, `✎` 응답 중, `⚙ Bash` 도구 인자 작성, `▶ Bash 5s` 도구 실행, `⚠` 멈춤 의심), 들어오는 노드(`← a, b`) 또는 `Start node`가 들어갑니다. 바로 아래 줄로 가는 간선은 상자 그림 문자 연결선(`│ ─ ┬ ┴ ▼`)으로 잇습니다. 박스 줄을 하나 이상 건너뛰는 간선(넓은 층이 줄바꿈된 경우, `a → c` 같은 건너뛰기)은 왼쪽 거터의 세로 레인으로 내려갑니다. 레인마다 출발·도착 줄이 따로 있어서, 다른 선을 지날 때는 합류(`┴`)가 아닌 교차(`┼`)로 그려집니다. 목적지가 같은 간선은 한 레인을 같이 쓰며, 레인은 최대 4개입니다. 테두리 색은 상태를 따릅니다(실행 중 cyan, 완료 green, 실패 red, 멈춤 의심 yellow, 대기 흐림). 노드를 선택하면 그 노드의 위·아래 경로 연결선과 박스는 진하게, 나머지는 흐리게 그립니다. 한 층이 박스 두 줄을 넘으면 선택·멈춤 의심·실패·실행 중 노드를 먼저 남기고 나머지를 `+19 more` 요약 박스 하나로 접으며, `f`로 펼치거나 다시 접습니다.
  - **레인 뷰**: `git log --graph`처럼 한 줄에 노드 하나를 두고, 진행 중인 간선마다 레인을 하나씩 그립니다. 모든 간선이 정확히 보이고, 같은 노드로 모이는 간선은 바로 한 레인에 합류해서 노드가 24개인 팬인도 폭이 좁게 유지됩니다.
  - **타임라인 뷰**: 노드마다 시작부터 끝(실행 중이면 지금)까지를 막대로 그리고, 시간축과 실행 시간을 붙입니다. 경과 시간 기준 가장 긴 의존 사슬(임계 경로)을 `◆`로 표시합니다.
- **Inspector 탭**: 맨 위 탭으로 DAG(`g`), Decisions(`j`), Context(`x`), Sessions(`s`), Board(`b`) 화면을 고릅니다. DAG 화면은 위의 세 뷰를 그대로 보여 주고, Decisions는 판단 기록을 페이지 단위로 넘기며 하나를 골라 상세를 펼칩니다. Context는 복원 블록과 노트를, Sessions는 세션 목록·충돌과 인계 제안·수락·취소 버튼을, Board(한국어 화면에서는 `보드`)는 모델이 그린 보드를 보여 줍니다([보드](#보드)). `/dag inspect <화면>`으로 바로 열 수도 있습니다.
- **Dependencies**: 모든 간선 목록.
- **Node details**: 노드별 테두리 카드. 실행 중인 노드는 펼쳐지고 나머지는 접힙니다. 펼치면 작업 요약, 에이전트·모델, 진행(전체 활동 문구), 시도 횟수·경과 시간이 보입니다.
- 실패·건너뜀 노드의 오류 목록과 키 안내.

토큰 없이 30초, 첫 토큰 없이 90초가 지나면 멈춤 의심으로 표시합니다.

패널을 열지 않아도, 모델이 작업 중이어도 프롬프트 아래 한 줄(`DAG <이름>: 3/7 완료 · 실행 중 2 · 실패 1`)이 이 세션의 진행 중인 실행을 보여 줍니다. 실행이 여럿이면 가장 최근에 바뀐 실행에 `+N개 실행`이 붙고, 진행 중인 실행이 없으면 사라집니다. 사람이 확인해야 하는 순간에만 토스트(12초)가 뜹니다: 자동 복구 후에도 노드가 실패했을 때(검증 실패는 별도 문구), 인계 제안을 받았을 때, 모델이 시작한 실행이 시작 승인을 기다리기 시작했을 때(`DAG <이름> 실행이 승인을 기다립니다`), 실패가 있는 채로 실행이 끝났을 때, Claude Code가 패널을 그리지 못했을 때. 평소 진행 상황에는 토스트가 없습니다.

이 세션에 진행 중인 실행이 있으면 프롬프트 바로 위에도 요약 밴드가 최대 세 줄로 나옵니다(터미널과 데스크톱, 모델이 작업 중일 때도 표시).

- **첫 줄**: 실행 이름과 상태 줄과 같은 수치입니다(`DAG <이름>  3/7 완료 · × 실패 1 · ? 권한 승인 대기 1 · ● 실행 중 2`). 급한 것부터 적어서, 폭이 모자라면 뒤쪽부터 `…`로 잘립니다. 시작 승인을 기다리는 실행이면 `● 실행 중 N` 자리에 노란 굵은 글씨의 `? 승인 대기 중`(영어 `? awaiting approval`)이 나옵니다.
- **둘째 줄**: 숫자 단축키 버튼입니다. `0`은 DAG 패널을 열고, `1`–`5`는 확인이 필요한 노드(실패 `×`, 권한 승인 대기 `?`, 실행 중 `●` 순서로 최대 5개)를 선택한 채 패널을 DAG 화면으로 엽니다. 프롬프트가 비어 있을 때 숫자 하나만 입력하고 잠시 기다리면 그 버튼이 눌리므로, 패널이 키보드 포커스를 얻지 못하는 모델 작업 중에도 쓸 수 있습니다. 버튼으로 연 패널은 사용자가 요청한 것이라 어떤 폭에서도 표시되고, 프롬프트가 비어 있으면 포커스도 받습니다. 노드 id가 길면 표시 폭 기준으로 `…`로 줄이고, 그래도 자리가 모자라면 덜 급한 노드부터 뺍니다.
- **셋째 줄**: Claude Code가 패널을 그리지 못하고 있을 때만 나오는 `패널 미표시: <이유>`입니다.

밴드는 주어진 폭과 줄 수를 넘지 않습니다. 한 줄만 쓸 수 있으면 버튼 줄만 남기고(수치는 프롬프트 아래 상태 줄에도 있습니다), 다른 mod가 밴드에 그린 내용은 그 아래에 그대로 둡니다. 설문(survey)이 밴드를 쓰는 동안과 진행 중인 실행이 없을 때는 아무것도 그리지 않습니다. 좁은 터미널에서 패널이 프롬프트 위에 열려 있는 동안에는 그 자리에 패널이 보이고, 패널을 닫으면 밴드가 다시 나옵니다(Claude Code 2.1.288에서 확인).

Claude Code는 mod가 요청 없이 연 패널을 좁은 터미널(144열 미만, 사용자가 한 번 직접 연 뒤에는 110열 미만)에서는 그리지 않고 대기시킵니다. 이때는 이유를 토스트로 한 번 알리고 밴드가 패널을 대신합니다. 확인할 노드가 없어도 밴드는 남고, `0`이나 `/dag`로 패널을 열어 실제로 그려지면 셋째 줄이 사라집니다.

노드 작업자가 도구 권한 승인을 기다리면(`classic.PermissionRequest`, 또는 최종 권한 판정이 `ask`인 노드 호출) 그래프·레인·타임라인·노드 카드·인스펙터의 해당 노드에 노란 `승인 대기: <도구>`(영어 `waiting: <tool>`) 표시가 붙고, 상태 줄에 `권한 승인 대기 N`이 더해지며, 대기 한 번마다 토스트 하나(`DAG <실행> › <노드> 노드가 권한 승인을 기다립니다`)가 뜹니다. 대기 상태는 토스트, 상태 줄, 프롬프트 위 밴드에 표시됩니다. 호출 ID를 알면 권한 대화 상자 아래에 한 줄을 붙이도록 `$.ui.notice`를 호출하지만, 이 줄을 그릴지는 호스트에 달려 있습니다(2.1.288 실측: 호출은 받아들여지지만 아무것도 그리지 않음). 이 줄에 의존하지 마세요. 표시는 그 호출이 진행되거나 거부될 때, 작업자의 다음 단계나 종료 때, 실행을 취소할 때 사라지며 체크포인트에 저장하지 않습니다.

> **주의:** DAG 패널이 키보드 포커스를 가진 상태에서는 패널이 권한 대화 상자로 갈 Enter를 가져갈 수 있습니다. 현재 mod API에는 패널의 포커스를 해제하는 호출이 없어 자동으로 돌려줄 수 없습니다. 노드가 `승인 대기` 상태가 되면 `Esc`로 포커스를 프롬프트에 돌려준 뒤 대화 상자에 답하세요(`/dag`로 직접 연 패널은 `Esc`에 닫히며, `/dag`로 다시 열 수 있습니다).

첫 웨이브 다음에 시작되는 노드는 Claude Code가 스트리밍 이벤트를 mod에 전달하지 않습니다. 그래서 이런 노드의 활동은 2초마다 노드 기록을 읽어 메시지 단위로 표시하고, stall 경고는 모델 대기가 5분을 넘을 때만 띄웁니다.


| 키                          | 동작                                      |
| -------------------------- | --------------------------------------- |
| `n` / `p`                  | 다음 / 이전 노드 선택                           |
| `d`                        | 상세 보기(task id, 보고서 경로, 답변)              |
| `t`                        | DAG 뷰와 Tasks 뷰(DAG에 속하지 않은 서브에이전트) 전환   |
| `c`                        | 끝난 실행 목록 펼치기·접기(실행이 둘 이상일 때)            |
| `v`                        | 보기 전환: 자동 → 그래프 → 레인 → 타임라인(이 프로젝트에 저장) |
| 탭 버튼 클릭                    | 그 보기로 바로 전환(이 프로젝트에 저장)                 |
| `f`                        | 그래프 뷰에서 넓은 층 펼치기·접기                     |
| `a` / `r`                  | 승인 대기 중인 실행을 승인 / 거절(승인 블록의 버튼과 같음)     |
| 카드의 `[-]` / `[+]`          | 그 노드 펼치기·접기(이 프로젝트에 저장)                 |
| 그래프를 클릭한 뒤 Tab / Shift-Tab | 다음 / 이전 노드 선택                           |
| 그래프를 클릭한 뒤 Space / Enter   | 선택한 노드 펼치기·접기                           |
| 그래프를 클릭한 뒤 ← / →           | 이전 / 다음 실행                              |
| Esc                        | 프롬프트로 돌아가기(`/dag`로 연 패널은 닫힘)            |
| 빈 프롬프트에서 `0`               | DAG 패널 열기(밴드 버튼)                        |
| 빈 프롬프트에서 `1`–`5`           | 밴드에 보이는 그 번호의 노드를 선택한 채 패널 열기           |


글자 단축키(`n` `p` `d` `t` `c` `v` `f`, 승인 대기 중인 실행이 보일 때는 `a` `r`도)는 패널이 키보드 포커스를 가진 동안 동작합니다. 프롬프트가 비어 있을 때 ctrl+x tab으로 패널에 포커스를 줍니다. mod의 Button 단축키는 숫자나 소문자 한 글자만 받으므로, Tab·Space·화살표는 그래프 영역을 클릭해 포커스를 준 뒤에만 동작합니다.

패널을 직접 닫으면 자동으로 다시 열리지 않습니다. `/dag`나 밴드의 `0`으로 다시 엽니다.

좁은 창에서는 패널이 프롬프트 위의 스크롤 영역으로 표시됩니다. 아래쪽 증거나 출처가 안 보이면 `ctrl+x tab`으로 패널에 포커스를 준 뒤 위·아래 화살표로 스크롤합니다.

패널과 프롬프트 위 띠는 terminal과 desktop 화면에만 그려집니다. vscode, mobile 같은 다른 화면(알 수 없는 화면 포함)에서는 패널을 열지 않고, 노드가 끝날 때마다 짧은 진행 메시지를, 실행이 끝나면 기존 요약 메시지를 텍스트로 보냅니다.

## 보드

보드는 모델이 흐름도, 호출 순서, 표, 핵심 코드 몇 줄을 한 곳에 그려 사용자에게 보여 주는 문서입니다. `mcp__dag-workflow__board` 도구로 만들고 고치며, `/dag` 패널의 Board(`보드`) 섹션에 그려집니다. `strict`에서도 메인 대화가 쓸 수 있는 도구입니다([강제](#강제)). 보드는 세션마다 따로 있고, `board_id`는 그 세션의 보드만 가리킵니다. `/dag-workflow:interview`와 `/dag-workflow:pm`은 질문하는 동안 이 보드에 진행 상황을 그립니다([정렬 스킬](#정렬-스킬-인터뷰와-pm)). `auto`에서 요청이 보드로 답할 일이라고 판단되면 프로토콜이 보드로 답하라고 알립니다([표시 방식 판단](#표시-방식-판단)). 보드 섹션의 블록 머리글을 누르면 그 블록을 프롬프트에 인용할 수 있습니다([블록 칩](#블록-칩)). 그 밖에는 사용자가 요청하거나 모델이 필요할 때 도구를 직접 호출합니다. DAG의 수명 주기는 보드 도구를 스스로 부르지 않습니다. 예전에 플러그인이 정산 때 그리던 결과 보드(요약, 노드 표, 실행 그래프, 쓰기 범위, 판단 기록)와 계획 스킬이 `start` 전에 그리던 계획 보드는 없어졌고, 실행 기록은 DAG 패널과 그 inspector가 담습니다.

도구 설명은 모델에게 무엇을 왜 다루는지 쓴 `section`을 먼저 두고, 그 뒤에 다이어그램(`flow` 또는 `sequence`) 하나, 마지막에 메커니즘을 담은 몇 줄의 `code_peek`을 쓰라고 안내합니다. 한 번에 블록 몇 개씩 나눠 그리고, 첫 `edit` 뒤에 `open`을 한 번 부르고, 끝내기 전에 `get`으로 읽어 확인하라는 안내도 있습니다.

### 보드 도구 액션

| 액션 | 입력 | 결과 |
| --- | --- | --- |
| `create` | `{title}` (1-80자) | `{board_id}`. id는 `board_<시각의 36진수>_<무작위 6자>` 모양입니다. 새 보드가 패널에서 선택된 보드가 됩니다 |
| `edit` | `{board_id, edits}` (edits 1-20개) | `{board_id, blocks, inserted}`. `blocks`는 고친 뒤 보드의 모든 블록 `[{id, type}]`, `inserted`는 이번 호출이 새로 만든 블록 id입니다. 고친 보드가 선택된 보드가 됩니다 |
| `get` | `{board_id}` | 보드 전체: `boardId`, `sessionId`, `title`, `createdAt`, `updatedAt`, `nextId`, `blocks`. `code_peek`, `trace`, `diff`는 `lines` 대신 줄 수 `lineCount`를 돌려줍니다 |
| `list` | 없음 | `{boards: [{board_id, title, blocks, updatedAt}]}`. 생성 순서이고, `blocks`는 블록 수입니다 |
| `open` | `{board_id}` | `{board_id, shown: true}`. 이 세션의 실행이 아직 끝나지 않았으면 `{board_id, shown: true, section: 'dag', hint}`이고 패널은 DAG 화면에 머뭅니다. 패널을 그릴 수 없는 화면이거나 사용자가 패널을 닫아 둔 상태면 `{board_id, shown: false, hint}`입니다 |
| `export` | `{board_id}` | `{board_id, markdown}`. 보드를 마크다운 한 편으로 직렬화합니다. 각 블록 위에 `<!-- b3 -->` 주석으로 블록 id를 남기고, `flow`·`sequence`는 mermaid(`flowchart LR`·`sequenceDiagram`)로 쓰고, `diff`는 `diff` 코드 펜스로 씁니다. `ref`가 있는 `code_peek`은 줄 범위 뒤에 `at <ref>`가 붙습니다 |

`edit`의 `edits`는 순서대로 적용하며 전부 성공하거나 아무것도 바뀌지 않습니다. 하나라도 거부되면 보드도 저장 파일도 그대로입니다. 글자 수는 앞뒤 공백을 지운 뒤 셉니다. 알 수 없는 필드는 오타를 조용히 버리지 않고 거부하며, 오류 메시지는 `edits[0]: nodes[0].label: must be 1-40 characters, got 0`처럼 몇 번째 edit의 어느 필드인지 알려 줍니다.

| `op` | 형식 | 동작 |
| --- | --- | --- |
| `insert` | `{op, block, afterId?}` | 새 블록을 `afterId` 블록 바로 뒤에 넣고, 없으면 맨 끝에 붙입니다. `block`에는 id가 없습니다. 보드가 붙입니다 |
| `update` | `{op, id, changes}` | 그 블록에 `changes`의 필드를 덮어쓴 뒤 블록 전체를 다시 검사합니다. 배열 필드(`rows`, `nodes` 등)는 통째로 바뀝니다. `changes`에는 필드가 하나 이상 있어야 하며, 빈 문자열 `""`은 선택 텍스트 필드를 지웁니다. `id`, `type`, `lines`는 바꿀 수 없습니다 |
| `replace` | `{op, id, block}` | 같은 id로 블록을 통째로 바꿉니다. 다른 종류로도 바꿀 수 있습니다 |
| `remove` | `{op, id}` | 블록을 지웁니다 |
| `move` | `{op, id, afterId?}` | 블록을 `afterId` 바로 뒤로 옮기고, 없으면 맨 끝으로 옮깁니다. 없는 id나 `afterId`가 자기 자신인 경우는 거부합니다 |

### 블록 종류

보드 하나에는 블록이 60개까지 들어갑니다. 글자 수 제한은 문자 수입니다. `title?`처럼 `?`가 붙은 필드는 생략할 수 있습니다.

| 종류 | 필드와 제한 |
| --- | --- |
| `section` | `title` (1-80자), `text?` (4,000자까지) |
| `callout` | `tone` (`info`, `decision`, `risk`, `warning` 중 하나), `text` (1-1,000자), `title?` (80자까지) |
| `table` | `columns` (1-6개, 각 1-80자), `rows` (0-30행, 한 행의 셀 수는 열 수와 같고 셀은 80자까지이며 빈 셀도 가능), `title?` (80자까지). `rows`는 비어 있어도 `[]`로 써야 합니다 |
| `code_peek` | `path`, `ref?` (64자까지), `start`, `end`, `note?` (200자까지), `title?` (80자까지). 아래 **code_peek** 설명 |
| `code` | `code` (1-4,000자, 40줄까지·줄 하나는 240자까지), `language?` (20자까지), `note?` (200자까지), `title?` (80자까지). 아래 **code·trace** 설명 |
| `trace` | `run`, `node`, `part` (`output`, `answer`, `error`, `verification` 중 하나), `note?` (200자까지), `title?` (80자까지). 아래 **code·trace** 설명 |
| `diff` | `ref` (1-64자, 필수), `path?` (300자까지), `note?` (200자까지), `title?` (80자까지). 아래 **diff** 설명 |
| `flow` | `nodes` (1-24개), `edges` (0-48개), `title?` (80자까지). 노드는 `id`, `label` (1-40자), `kind?` (`process`, `decision`, `terminal`), `note?` (80자까지)이고, 간선은 `from`, `to`, `label?` (40자까지), `style?` (`dashed` — 임시·비동기 관계에)입니다. `edges`는 비어 있어도 `[]`로 써야 합니다 |
| `sequence` | `participants` (2-8명), `steps` (1-40개), `title?` (80자까지). 참여자는 `id`, `label` (1-24자)이고, 단계는 `from`, `to`, `label` (1-60자), `kind?` (`call`, `return`, `async`, `note`), `note?` (80자까지 — 단계 아래 흐린 줄로 그립니다)입니다 |
| `board_ref` | `board` (이 세션의 다른 보드 id), `title?` (80자까지). 아래 **board_ref·divider** 설명 |
| `divider` | 필드 없음. 아래 **board_ref·divider** 설명 |

**블록 id**: 블록 id는 `b1`, `b2`처럼 `b<n>`이고, 보드마다 세는 카운터(`nextId`)가 붙입니다. 카운터는 늘기만 하므로 지운 블록의 id를 다른 블록이 이어받는 일이 없습니다. 패널은 블록마다 `[b3] flow · 제목` 머리글을 보여 주기 때문에, 사용자가 "b3을 고쳐 줘"라고 말하면 그 블록 하나를 가리킵니다. 머리글은 누르면 블록을 프롬프트에 칩으로 넣는 버튼이기도 합니다([블록 칩](#블록-칩)).

**flow**: 노드 `id`와 sequence의 참여자 `id`는 영문, 숫자, `_`, `-`, `.`로 1-32자이고 블록 안에서 겹치지 않아야 합니다. 간선은 같은 블록의 노드 id를 가리켜야 하고, 자기 자신으로 가는 간선과 같은 `from`·`to`를 두 번 쓰는 것은 거부합니다. 간선이 순환을 이루면(`A -> B -> A`) 거부하고 오류 메시지가 순환 경로를 알려 줍니다. 반복은 간선 대신 노드의 `note`나 `callout`에 글로 적습니다. `sequence`는 순환 규칙이 없고, `from`과 `to`가 같은 참여자인 자기 호출 단계도 쓸 수 있습니다.

**code_peek**: 파일의 몇 줄을 보여 주는 블록입니다.

- `path`는 1-300자의 프로젝트 상대 경로입니다. 절대 경로, 드라이브 문자, `..`, 대소문자와 관계없이 `.claude` 구간이 들어간 경로는 거부합니다.
- `start`와 `end`는 1부터 세는 정수이고 `end`가 `start`보다 앞설 수 없습니다. 한 블록은 40줄까지(`end - start`가 40 미만)입니다.
- `ref?`가 없으면 줄은 **블록을 그릴 때** `<프로젝트 루트>/<path>`에서 읽어 보드에 저장합니다. 파일이 나중에 바뀌어도 보드에는 그때 논의한 줄이 그대로 남습니다. 새로 읽으려면 `update`로 `path`, `ref`, `start`, `end` 중 하나를 바꾸거나 `replace`합니다. `note`와 `title`만 바꾸면 저장된 줄을 유지합니다. 줄 하나는 240자까지만 저장하고 넘으면 `…`로 자릅니다. 파일 내용 일부가 `.claude/dag/boards/`에 복사됩니다.
- `ref`가 있으면 워킹 트리 대신 `git show <ref>:<path>`로 그 시점의 파일을 읽습니다(프로젝트 루트에서 실행하며 `path`는 프로젝트 루트 기준). 예: 직전 커밋 버전은 `HEAD~1`, 다른 브랜치는 `main`. 읽은 줄은 `ref`를 쓰지 않을 때와 같이 그릴 때의 내용으로 저장하고, `ref`·`path`·`start`·`end` 중 하나를 바꾸는 `update`는 줄을 다시 읽습니다. `update`에서 `ref`를 `""`로 보내면 워킹 트리 읽기로 돌아갑니다.
- `ref`는 1-64자이고 영문, 숫자, `_ . / ~ ^ { } @ -`만 쓸 수 있으며 첫 글자는 영문, 숫자, `_`, `@`만 됩니다(`-`로 시작해 git 옵션으로 읽히는 것을 막습니다). 글자 검사는 `a..b` 같은 범위 모양도 통과시키지만, `git show`가 그 파일을 읽지 못하면 아래처럼 읽기 실패로 거부합니다.
- 파일을 읽을 수 없거나(`ref`가 있으면 `git show`가 실패한 경우, 알 수 없는 `ref`와 그 시점에 없는 파일 포함) 범위가 파일 끝을 넘으면(`... reach past the end of the file, which has N lines`, `ref`가 있으면 `path@ref`와 그 버전의 줄 수를 알려 줍니다) `invalid_board_edit`로 거부합니다. 마지막 줄바꿈은 새 줄로 세지 않습니다.
- 패널의 머리글 줄은 `ref`가 있으면 `<path>@<ref>:<start>-<end>`(예: `src/a.ts@HEAD~1:8-9`)로 시점을 밝히고, 없으면 `<path>:<start>-<end>` 그대로입니다. `export`는 `` `path` (L8–L9 at main~2) `` 꼴로 씁니다.
- 한계: 같은 `edit` 호출에서 방금 `insert`한 `code_peek`의 범위나 `ref`를 `update`로 옮기면 `could not read …`로 실패합니다. 범위와 `ref`는 다른 호출에서 옮깁니다.

**code·trace**: `code`는 아직 파일에 없는, 모델이 제안하는 코드 조각을 보여 주는 블록입니다. 보낸 내용을 그대로 저장하므로 파일을 읽지 않고 경로 검사도 없습니다. `language`는 패널의 코드 머리글과 `export`의 코드 펜스에 쓰이는 이름입니다.

`trace`는 이 세션의 실행 한 번에서 노드 하나의 산출물을 인용하는 블록입니다.

- 모델은 `run`(실행 id `dag_…`), `node`(그 실행의 노드 id), `part`만 보내고 `lines`는 보낼 수 없습니다. 호스트가 `.claude/dag/runs/<run>.json` 체크포인트를 읽어 줄을 채웁니다. 다른 세션의 실행이거나 없는 실행·노드이면 `invalid_board_edit`로 거부합니다.
- `part`가 `output`·`answer`·`error`이면 노드의 그 필드를, `verification`이면 노드의 검증 보고서 파일을 읽습니다. 노드에 그 내용이 없으면 거부합니다.
- `code_peek`처럼 줄은 블록을 그릴 때 읽어 저장하므로 실행 기록이 나중에 바뀌어도 보드에는 그때 본 내용이 남습니다. 40줄까지만 저장하고 넘으면 앞의 39줄과 `… +N more lines` 한 줄로 자르며, 줄 하나는 240자까지만 저장합니다. 새로 읽으려면 `update`로 `run`·`node`·`part` 중 하나를 바꾸거나 `replace`합니다. `note`와 `title`만 바꾸면 저장된 줄을 유지합니다.

**diff**: git 변경을 인용하는 블록입니다. `code_peek`처럼 모델은 `lines`를 보낼 수 없고 호스트가 채웁니다.

- `ref`는 필수이고 `code_peek`의 `ref`와 같은 모양입니다(`HEAD~1`, `main`, `main..feature` 같은 범위도 됩니다). `path?`는 1-300자의 프로젝트 상대 경로이며 `code_peek`의 `path`와 같은 검사를 받습니다. 하나의 파일로 diff를 좁힙니다.
- 호스트가 프로젝트 루트에서 `git diff <ref>`를 실행해 출력 줄을 저장하고, `path`가 있으면 `-- <path>`를 붙여 그 파일만 봅니다. 색과 외부 diff 도구 설정과 관계없이 평문 unified diff 줄을 받습니다. `path`는 글자 그대로 한 파일 경로로 읽고 패턴으로 읽지 않습니다.
- diff가 비어 있거나(`... is empty; nothing differs`) git이 읽지 못하면(알 수 없는 `ref`, git 실행 실패, 저장소 밖 경로) `invalid_board_edit`로 거부하고 보드는 그대로입니다.
- `trace`와 같은 규칙으로 저장합니다. 40줄까지만 저장하고 넘으면 앞의 39줄과 `… +N more lines` 한 줄로 자르며, 줄 하나는 240자까지만 저장합니다. 그릴 때 읽은 줄이 남고, 새로 읽으려면 `update`로 `ref`나 `path`를 바꾸거나 `replace`합니다. `note`와 `title`만 바꾸면 저장된 줄을 유지합니다. `get`은 `lines` 대신 줄 수 `lineCount`를 돌려줍니다. 같은 `edit` 호출에서 방금 `insert`한 `diff`의 `ref`·`path`를 `update`로 바꾸면 `code_peek`처럼 `could not read …`로 실패합니다.
- 패널의 머리글 줄은 git 인자 그대로 `<ref>`(예: `main`), `path`가 있으면 `<ref> -- <path>`(예: `main..feature -- src/a.ts`)이고, 줄은 `trace`처럼 1부터 번호를 매깁니다. 패널은 `+`·`-` 줄에 색을 입히지 않습니다. `export`는 `` `ref · path` `` 한 줄 뒤에 `diff` 코드 펜스를 씁니다. 파일 내용 일부가 `code_peek`처럼 `.claude/dag/boards/`에 복사됩니다.

**board_ref·divider**: `board_ref`는 같은 세션의 다른 보드를 가리키는 링크 블록입니다. `board`에는 `create`/`list`가 돌려주는 `board_id`를 쓰고, 편집 시점에 세션에 존재하는 보드여야 하며 자기 보드는 가리킬 수 없습니다(없으면 `invalid_board_edit`). 보드는 지우는 동작이 없으므로 링크가 끊길 일이 없습니다. 패널에서는 `→ Board: <title 또는 board_id>` 줄이 버튼이라 누르면 그 보드로 선택이 바뀌고, `export`에서는 대상을 가리키는 인용 줄이 됩니다. `divider`는 필드가 없는 가로 구분선입니다. `update`로 바꿀 필드가 없으므로 내용 변경은 `replace`로만 합니다. `export`에서는 `---`입니다.

**점선 간선과 단계 `note`**: flow 간선의 `style?: 'dashed'`는 연결선 도형 자체가 아니라 글자로 표시됩니다 — 상자 보기에서는 도착 노드의 들어오는 간선 목록에 `╌` 접두사가 붙고, 좁은 목록 보기에서는 화살표가 `⇢`가 됩니다(연결선 도형은 DAG 패널과 같은 그리기를 공유합니다). `export`의 mermaid에서는 `-.->`로 씁니다. sequence 단계의 `note?`는 그 단계 아래(화살표 아래나 lifeline 옆)에 흐린 줄로 그려지고, `export`에서는 `Note over <from>,<to>: <note>`가 됩니다.

### 보드 섹션

- 패널의 Board 섹션(한국어 화면에서는 `보드`)은 위쪽 탭에 DAG(`g`), Decisions(`j`), Context(`x`), Sessions(`s`)와 함께 `b` 키로 고를 수 있고, `/dag inspect board`로 바로 열 수 있습니다. 사용자가 직접 연 패널이므로 닫아 둔 패널도 다시 열리고 키보드 포커스를 받습니다.
- 한 번에 보드 하나를 보여 줍니다. `create`, `edit`, `open`이 고른 보드가 보이고, 고른 보드가 없으면 가장 나중에 고친 보드가 보입니다. 제목 뒤에 `(2/3)`처럼 순번이 붙습니다. 보드가 없으면 안내 문구만 나옵니다.
- 블록은 위에서 아래로 그려지고, 블록 단위로 한 페이지에 약 60줄씩 나눕니다. 60줄보다 긴 블록은 혼자 한 페이지를 차지하고 `… N줄 더`로 잘립니다. 페이지가 둘 이상이면 `이전 페이지`·`다음 페이지`(영어 `prev page`·`next page`) 버튼과 `페이지 1/2` 표시가 나옵니다.
- 보드가 둘 이상이면 `이전 보드`·`다음 보드`(영어 `prev board`·`next board`) 버튼으로 생성 순서대로 넘기며, 끝에서 처음으로(처음에서 끝으로) 돌아가고 첫 페이지로 갑니다.
- `open {board_id}`는 그 보드를 선택하고 Board 섹션의 첫 페이지로 정하며 보고 있던 판단 상세를 닫은 뒤, 모델이 시작한 실행처럼 패널을 키보드 포커스 없이 엽니다. 이 세션의 실행이 끝나지 않았을 때는 패널을 Board 섹션으로 바꾸지 않습니다(다음 항목). 사용자가 직접 닫은 패널은 다시 열지 않고 `shown: false`와 `/dag inspect board`를 안내하는 `hint`를 돌려줍니다([DAG 패널](#dag-패널)). 패널을 그리지 못하는 화면(terminal과 desktop 밖)에서도 `shown: false`이며 보드는 저장됩니다. `shown: true`는 패널을 열도록 요청했다는 뜻이라, 좁은 터미널에서는 Claude Code가 요청 없이 연 패널을 대기시킬 수 있습니다([DAG 패널](#dag-패널)).
- **실행이 끝나지 않았을 때의 `open`**: 이 세션의 실행이 실행 중이거나 일시정지이거나 시작 승인을 기다리는 동안(끝나지 않은 상태)에는 사용자가 DAG를 보고 있으므로 `open`이 패널을 Board 섹션으로 바꾸지 않고 DAG 화면에 둡니다. 그 보드를 선택하고 첫 페이지로 정하는 일, 패널을 키보드 포커스 없이 여는 일은 그대로입니다. 대신 토스트를 한 번(12초) 띄웁니다. 영어 `Board updated: <보드 제목> · press b in the /dag pane`, 한국어 `보드 갱신: <보드 제목> · /dag 패널에서 b`입니다. 사용자가 `b`를 누르면 방금 선택한 보드가 열립니다. 도구 응답은 `{board_id, shown: true, section: 'dag', hint}`이고, `hint`는 실행이 진행 중이라 패널이 DAG에 머무니 사용자에게 `b`를 누르라고 알리라고 모델에게 말해 줍니다. 끝난 실행만 있거나 실행이 없으면 예전처럼 Board 섹션으로 바꾸고 토스트 없이 `{board_id, shown: true}`를 돌려줍니다. 패널을 그리지 못하는 화면이거나 사용자가 패널을 닫아 둔 경우는 실행이 끝났는지와 관계없이 `shown: false`이고 토스트도 없습니다. 이미 Board 섹션을 보고 있을 때 다른 보드를 `open`해도 응답과 토스트는 같지만 화면은 그대로 Board 섹션에 머뭅니다.
- 블록 글은 모델이 쓴 것이므로 제어 문자를 지우고 줄마다 패널 폭에 맞춰 자릅니다.

### 블록 칩

보드 섹션의 블록 머리글(`[b3] flow · 제목`) 한 줄은 버튼입니다. 누르면 그 블록의 칩을 프롬프트 입력창의 커서 위치에 넣습니다. 블록이 있는 페이지는 `페이지 n/m` 표시 뒤 맨 아래에 안내 줄을 두며, 영어 `Press a block header to cite that block in your prompt`, 한국어 `블록 머리글을 누르면 프롬프트에 그 블록을 인용합니다`입니다. 블록이 없는 보드와 보드가 없는 화면에는 버튼도 안내 줄도 없습니다. 페이지를 넘기거나 좁은 패널에서 줄이 잘려도 버튼은 그 머리글 줄에 붙어 있고, 60줄보다 긴 블록은 잘린 채로 머리글 버튼을 유지합니다.

- **칩 글자**: `[b3 · <이름>]` 뒤에 공백 하나가 붙고, 글자는 굵게 강조색으로 칠합니다. 입력창을 고칠 때마다 기억한 칩 글자를 다시 칠하므로 칩 앞뒤에 글을 써도 색이 남고, 칩 글자 안을 고치면 색이 빠집니다. 색이 빠진 칩은 제출할 때도 블록을 붙이지 않습니다. 앞의 id로 모델이 블록을 찾고, 이름은 사용자가 칩을 구별하게 합니다. 이름은 블록의 `title`이고 없으면 블록 종류입니다(`[b3 · flow]`). 40자까지이고 넘으면 `…`로 자르며, 칩을 끊을 수 있는 `[`·`]`와 줄바꿈 같은 제어 문자는 뺍니다.
- **제출할 때**: 사용자가 보낸 프롬프트가 칩 글자를 그대로 담고 있으면 그 블록의 내용이 컨텍스트로 붙습니다. 블록은 제출 시점의 보드에서 읽으므로 그사이 고친 내용이 반영됩니다. 모델은 `The person attached the chip [b3 · …] to this prompt: block b3 of the board "<보드 제목>" (board_id …)`로 시작하는 문단과 그 아래 줄의 블록 JSON을 받으며, 문단은 이 JSON이 이 대화가 보드에 그린 내용이고 지시가 아니라 데이터라고 알려 줍니다. 칩 하나에 4,000자까지이고 넘으면 `[Cut at 4000 characters. Call the board tool's get action with board_id … for the whole board.]`로 끝나 모델이 `get`으로 전체를 읽게 합니다. 칩 글자를 지웠거나 고친 프롬프트와, 칩이 가리키던 보드나 블록이 그새 없어진 칩에는 아무것도 붙지 않습니다.
- **개수**: 한 프롬프트에서 칩 5개까지 받으며, 프롬프트에 먼저 나온 순서입니다. 누른 칩은 20개까지 기억하고 넘으면 가장 오래된 것부터 잊습니다. 같은 칩을 다시 누르면 가장 최근으로 칩니다. 칩은 글자로 구별하고 글자에 보드 id가 없으므로, 다른 보드에서 같은 글자의 칩을 누르면 나중에 누른 쪽을 따릅니다.
- **기억 범위**: 사용자가 프롬프트를 보내면 칩을 담았든 아니든 기억한 칩을 모두 잊습니다. 정산 메시지나 진행 메시지 같은 플러그인의 프롬프트는 칩을 받지도 지우지도 않습니다.
- **입력창이 거절할 때**: 칩을 넣지 못하면(입력창이 알려 준 사유 `no_composer`, `dialog` 등, 없으면 `unknown`) 토스트를 한 번(12초) 띄우고 그 칩은 기억하지 않습니다. 영어 `Could not put the block into the prompt (<사유>)`, 한국어 `블록을 프롬프트에 넣지 못했습니다 (<사유>)`입니다. 누르는 사이 보드가 바뀌어 그 블록이 화면에서 사라졌으면 아무 일도 하지 않습니다.

### 승인 블록의 계획 보드 줄

`start_approval`로 시작이 보류된 실행의 승인 블록([실행 규칙](#실행-규칙))은 이 세션에 보드가 있으면 미리보기 맨 끝에 한 줄을 더해 보드를 가리킵니다. 영어 `Plan board: <보드 제목> · press b to view`, 한국어 `계획 보드: <보드 제목> · b로 보기`입니다. 제목은 이 세션에서 `updatedAt`이 가장 늦은 보드(만든 순서가 아니라 마지막으로 고친 순서이고, 같으면 목록에서 나중 보드)의 것이며, 줄은 패널 폭에 맞춰 잘립니다. 줄의 이름은 `계획 보드`이지만 보드의 내용은 가리지 않고 이 세션에서 마지막으로 고친 보드를 그대로 가리킵니다. 세션에 보드가 없으면 줄도 없습니다. 이 줄은 DAG 패널의 승인 블록에만 있고 `/dag status`의 미리보기에는 없습니다. 인터뷰나 PM으로 그린 보드가 세션에 남아 있으면, 이어서 계획한 실행을 승인하려는 사용자가 `b`로 그 보드를 다시 볼 수 있습니다.

### 보드 저장과 보관

- 파일은 `.claude/dag/boards/<세션 id>.json`이고 세션 하나에 파일 하나, 보드는 여러 개입니다. 형식은 `{schemaVersion: 1, sessionId, boards}`이며 들여쓰기 2칸 JSON에 끝 줄바꿈이 붙습니다.
- `create`나 `edit`가 성공한 뒤에만 씁니다. 파일 쓰기가 실패하면 메모리의 보드도 바뀌지 않습니다.
- 이전 버전이 쓴 파일의 보드에 `run` 필드가 있어도 읽을 때 버립니다.
- 세션 시작 때 읽고, `/clear`·재개·포크로 세션 id가 바뀌면 새 id의 파일을 다시 읽습니다. 읽을 때 보드와 블록을 `edit`와 같은 검사로 확인합니다. 파일이 없으면 보드 없이 시작합니다. 깨졌거나 규칙을 어기거나 다른 세션 id를 가진 파일은 로그(`could not load <경로>: board file: ...`)에 남기고 지우지 않으며, 그 세션은 보드 없이 시작해 다음 `create`가 파일을 새로 씁니다.
- 보관은 `retention_days` 설정을 따릅니다. 세션을 시작할 때 `context/`, `decisions/`의 파일과 같은 규칙으로 정리합니다([보관 기간](#보관-기간)). 수정 시각이 기준보다 오래됐고 현재 세션·활성 세션·남은 실행이 참조하는 세션의 것이 아니면 지우며, `retention_days`가 `0`이면 지우지 않습니다.

### 보드 오류 코드

| 코드 | 조건 |
| --- | --- |
| `invalid_request` | 알 수 없는 `action` |
| `invalid_board_title` | `create`의 `title`이 1-80자가 아님 |
| `unknown_board` | `board_id`가 이 세션의 보드가 아님(`edit`, `get`, `open`). `list`로 확인합니다 |
| `invalid_board_edit` | `edits`가 1-20개 배열이 아님, 알 수 없는 `op`나 필드, 블록 검사 위반(위 표의 제한, flow 순환·중복·존재하지 않는 노드, 60개 초과), `id`·`type`·`lines` 변경, `code_peek` 파일(`ref`가 있으면 그 시점의 파일)을 읽을 수 없음 또는 범위가 파일 끝을 넘음, `diff`가 비었거나 git이 읽지 못함, `ref` 모양 위반 |
| `unknown_block` | `afterId`나 `update`·`replace`·`remove`의 `id`가 보드에 없음. 메시지에 보드의 블록 id가 나열됩니다 |
| `hook_<종류>` | 훅 자체가 실패함. 메시지는 `The board tool failed: ...`로 시작합니다 |

보드 파일을 읽지 못한 경우의 `invalid_board_file`은 모델에게 돌려주지 않고 로그에만 남습니다.

| `anti_slop_scan`               | `true`    | Edit·Write가 추가한 줄을 anti-slop 패턴으로 검사해 걸린 것을 모델에게 알림([의미 없는 코드 차단](#의미-없는-코드-차단-anti-slop)). 모델 호출 없음 |
| `anti_slop_skip`               | `[]`      | 스캔이 보고하지 않을 패턴 id 목록. 예: 이유 없는 캐스트를 허용하는 저장소의 `unreasoned-assertion` |
| `secure_scan`                  | `true`    | semgrep이 설치되어 있으면 Edit·Write가 추가하는 줄에 KISA 규칙을 실행(`block` 규칙은 쓰기 전에 거부)하고, 보안 검토 실행의 변경에서 나온 히트를 검증 노드가 붙는 후보로 더함([Semgrep 규칙 스캔](#semgrep-규칙-스캔)) |
| `trajectory_log`               | `false`   | 실행마다 노드 시도의 프롬프트·답·검증·검토 노트·diff·토큰·도구 호출 기록과 메인 대화의 턴을 `.claude/dag/trajectories/`에 남김([실행 기록](#실행-기록-trajectory)). `retention_days`로 지우지 않음 |
| `review_ledger`                | `true`    | 리뷰 수정 라운드가 실패한 리뷰어의 지적과 고치기 전 파일 복사를 남기고, 다시 도는 `review-spec`·`review-standards`에 지적과 수정 diff를 전달([자동 복구](#자동-복구)). `false`면 장부 이전 프롬프트 |


### 보관 기간

세션을 시작할 때 `retention_days`보다 오래된 다음 항목을 지웁니다. 현재 세션과 활성(60초 안에 갱신한) 세션의 것은 남깁니다.

- 다른 세션의 종료(또는 일시 정지)된 실행 체크포인트 `runs/<run_id>.json`과 그 보고서·검증 증거 폴더 `runs/<run_id>/`
- 어느 체크포인트에도 속하지 않는 `runs/dag_*` 폴더(시각과 관계없이 지움. 같은 이름의 `.json`이 있으면 읽을 수 없어도 남김)
- 남은 실행이 참조하지 않는 세션의 `context/<session>.json`, `decisions/<session>.json`, `boards/<session>.json`(파일 수정 시각 기준. 보드는 [보드 저장과 보관](#보드-저장과-보관))
- 갱신이 멈춘 세션의 세션 기록(플러그인 저장소 키)

삭제 실패는 로그에 남기고 세션 시작은 계속합니다.
